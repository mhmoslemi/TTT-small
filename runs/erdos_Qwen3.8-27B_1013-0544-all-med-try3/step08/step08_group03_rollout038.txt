- h[j] -= δ/(n-1) for all j ≠ i

This preserves the sum and maintains bounds if δ is small enough. The constraint is:
- 0 ≤ h[i] + δ ≤ 1 → -h[i] ≤ δ ≤ 1-h[i]
- 0 ≤ h[j] - δ/(n-1) ≤ 1 for all j ≠ i → -(n-1)*(1-h[j]) ≤ δ ≤ (n-1)*h[j] for all j≠i

So the max allowed δ is: min(1-h[i], (n-1)*min_{j≠i} h[j])
And the min allowed δ is: max(-h[i], -(n-1)*max_{j≠i}(1-h[j]))

Let me implement this approach. The coordinate update becomes:
1. Compute the optimal t for h[i] (as before, ignoring the sum constraint)
2. δ = t_opt - t_old
3. Clamp δ to the feasible range
4. Apply: h[i] += δ, h[j] -= δ/(n-1) for all j≠i

This should work! Let me code it up.

Actually wait, I realize there's a subtlety. When I change h[i] and also change all other h[j] by a small amount, the "slopes" for the coordinate update of h[i] are slightly different from what I computed (because the other coordinates also changed). But for a first-order approximation, this is fine.

Let me think about the computational complexity:
- Per coordinate update: O(n) to compute slopes, O(n * log(precision)) for binary search
- Per full pass: O(n^2 * log(precision))
- For n=300: 300 * 300 * 30 ≈ 2.7 million operations per pass
- For n=500: 500 * 500 * 30 ≈ 7.5 million operations per pass

This is very fast! We can do many passes.

So per coordinate: O(n) for slopes + O(n * log(prec)) for binary search = O(n * log(prec)).

Per full pass: O(n^2 * log(prec)). For n=300: 300*300*30 ≈ 2.7M. Very fast.
