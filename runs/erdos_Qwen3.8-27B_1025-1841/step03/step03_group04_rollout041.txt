In Phase 3, it tries values [0, 1, 0.25, 0.75] and steps [0.005, 0.01, 0.02, 0.05]. The issue is that `make_feasible` is called after each trial, which adjusts ALL elements to maintain the sum constraint. This means changing one element also changes others, potentially undoing progress.

A better approach for coordinate descent under a sum constraint:
- When changing h[j] from old_val to new_val, the "excess" (new_val - old_val) needs to be distributed to other elements to maintain the sum.
- If we increase h[j] by δ, we need to decrease the sum of other h[i] by δ. The simplest way is to distribute -δ/(n-1) to all other elements.
- But this might push some elements below 0. A better way is to distribute only to elements that have room.

This "paired update" approach avoids the expensive make_feasible call and gives more predictable behavior.

Let me implement this:

```python
def coordinate_step(h, j, new_val, n):
    """Try to set h[j] = new_val while maintaining sum(h) = n/2."""
    old_val = h[j]
    delta = new_val - old_val
    if abs(delta) < 1e-15:
        return h
    h = h.copy()
    h[j] = new_val
    # Distribute -delta to other elements
    others = np.arange(n)
    others = others[others != j]
    # Find elements with room to absorb the change
    if delta > 0:
        # Need to decrease others
        mask = h[others] > 0
    else:
        # Need to increase others
        mask = h[others] < 1.0
    if not np.any(mask):
        return h  # Can't make the change
    available = others[mask]
    # Distribute proportionally or uniformly
    h[available] += -delta / len(available)
    # Check bounds
    if np.any(h < -1e-12) or np.any(h > 1 + 1e-12):
        # Fallback to make_feasible
        h = make_feasible(h, n)
    return h
```
