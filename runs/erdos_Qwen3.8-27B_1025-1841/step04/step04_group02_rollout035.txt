- n = b-k (affects the h[n+k] factor, since n+k = b)

But some of these might be the same:
- a = a-k iff k=0
- a = b-k iff k = b-a
- b = a-k iff k = a-b
- b = b-k iff k=0
- a-k = b-k iff a=b (impossible)

So the distinct affected n values are at most 4 (could be fewer if some coincide).

For each affected n, I need to check if it's in the valid range (0 ≤ n < n AND 0 ≤ n+k < n).

For each valid affected n:
  old_contrib = h[n+k] * (1-h[n])
  new_contrib = h'[n+k] * (1-h'[n])
  where h' differs from h only at positions a and b.

This is O(1) per affected n, so O(1) per lag k!

And I only need to evaluate this for k values where at least one of {a, b, a-k, b-k} is in the valid range. The valid range for n is 0 ≤ n < n and 0 ≤ n+k < n, which means -min(n, n-1-k) ≤ k ≤ n-1-max(n, 0) ... this is getting complicated.

Let me just say: for a given swap (a,b), the delta is non-zero only for k values where at least one of a, b, a-k, b-k is in the range [max(0,-k), min(n-1, n-1-k)].

In practice, for most k values, none of these are in range, so the delta is 0. The non-zero k values form a bounded set.

For a practical implementation, I can:
1. Determine the range of k values where delta might be non-zero
2. For each such k, compute the delta in O(1)
3. Update the correlation array

The range of k where delta is non-zero:
- k such that a is valid: -a ≤ k ≤ n-1-a
- k such that b is valid: -b ≤ k ≤ n-1-b
- k such that a-k is valid: a-(n-1) ≤ k ≤ a
- k such that b-k is valid: b-(n-1) ≤ k ≤ b

Union: [min(-a, -b, a-n+1, b-n+1), max(n-1-a, n-1-b, a, b)]

For typical a, b in [0, n-1], this range is approximately [-(n-1), n-1], i.e., all k values. So in the worst case, I still need O(n) per swap.

OK so the total cost is O(n) per swap evaluation, and I want to do O(n) swaps (one per iteration of greedy), so total O(n²) for the greedy phase. For n=960, that's about 921600 operations, which should be fast.

But wait, I also need to find the BEST swap among O(n²) candidates. If I evaluate each in O(n), that's O(n³) total. That's too slow.

Solution: use a heuristic to limit the number of candidate swaps.

**Heuristic**: Only consider swaps where at least one of the positions is "involved" with the peak lag. Specifically:
- If the peak is at lag k*, then "involved" positions are those a where h[a]=1 and h[a-k*]=0 (a is the "1" in a bad pair at lag k*), or those b where h[b]=0 and h[b+k*]=1 (b is the "0" in a bad pair at lag k*).

There are at most O(n) such positions for each type, so at most O(n²) candidate swaps. But I can further reduce by only trying the "best" few.

Actually, let me just try all swaps of the form:
- a where h[a]=1 and (a-k* is valid and h[a-k*]=0): these are "bad 1s"
- b where h[b]=0 and (b+k* is valid and h[b+k*]=1): these are "bad 0s"

And for each pair (a, b), compute the delta at the peak lag only (O(1)). Sort by delta and try the top few.

This is O(n²) to enumerate + O(n log n) to sort + O(few * n) to evaluate the top candidates. Total O(n²) per iteration.

For n=960, n² ≈ 921600. With maybe 100 iterations, that's 92M operations. Should be fine.

Actually wait, I realize I'm overcomplicating this. Let me just use a simpler but effective approach:

**Simplified algorithm:**

1. Start with binary h
2. Compute correlation
3. Find peak lag k*
4. Generate candidate swaps:
   - For each a where h[a]=1: candidate to swap with b = a + k* (if valid and h[b]=0)
   - For each a where h[a]=1: candidate to swap with b = a - k* (if valid and h[b]=0)  
   - For each b where h[b]=0: candidate to swap with a = b + k* (if valid and h[a]=1)
   - For each b where h[b]=0: candidate to swap with a = b - k* (if valid and h[a]=1)
5. For each candidate, estimate the new max correlation (compute delta at peak)
6. Apply the best swap
7. Repeat

This gives O(n) candidates per iteration, each evaluated in O(1) (just the peak delta). Then verify by computing the actual new max in O(n²) (the correlate). Total: O(n) + O(n²) per iteration.

For n=960 and 1000 iterations: 1000 * (960 + 921600) ≈ 922M operations. In Python with numpy, the correlate is the bottleneck at ~1M ops per call, so 1000 calls would take maybe 1-2 seconds. That's fine!
