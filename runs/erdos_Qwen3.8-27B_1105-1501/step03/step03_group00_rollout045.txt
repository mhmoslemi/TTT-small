This is O(m) per coordinate (after computing a_r and b_r), and O(n*m) per full pass. For n=64, m=127, that's about 8128 operations per pass. Very fast!

The key question is: does coordinate descent converge to a good solution? For convex problems, it converges to the global optimum. For non-convex problems, it converges to a local optimum. Our problem is non-convex (the objective is the max of quadratic functions, which is not convex in general).

But wait - I showed that for fixed h[-i], the objective is convex in h[i] (it's the max of linear functions). So each coordinate step is exact. The question is whether the overall coordinate descent converges to a good local optimum.

This is similar to block coordinate descent, which is well-studied. For non-convex problems, it can get stuck in bad local optima, but it's often quite effective.

Moreover, we can cycle through coordinates in random order to escape some local optima. And we can combine it with the p-norm approach for a smoother overall direction.

def _coord_descent(h, n_passes=100, order='random'):
    n = len(h)
    m = 2 * n - 1
    h = h.copy()
    best_c5 = _exact_c5(h)
    rng = np.random.default_rng(42)
    
    for _pass in range(n_passes):
        if order == 'random':
            perm = rng.permutation(n)
        else:
            perm = range(n)
        
        for i in perm:
            # Compute a_r and b_r for each score r
            # s_r = sum of h[j]*(1-h[j+d]) over valid j
            # Terms involving h[i]:
            #   As first factor: h[i]*(1-h[i+d]) for lag d where i+d < n, d >= 0
            #                    and h[i]*(1-h[i-g]) for lag -g where i-g >= 0... 
            #                    wait, I need to be more careful.
            
            # Actually, let me just compute the scores with h[i] set to 0 and h[i] set to 1,
            # then s_r(x) = s_r(0) + x * (s_r(1) - s_r(0))
            
            saved = h[i]
            h[i] = 0.0
            s0 = _scores(h)  # s_r at h[i] = 0
            h[i] = 1.0
            s1 = _scores(h)  # s_r at h[i] = 1
            h[i] = saved
            
            # s_r(x) = s0[r] + x * (s1[r] - s0[r])
            # We want to minimize max_r s_r(x) over x in [0, 1]
            # subject to the sum constraint... 
            # Actually, changing h[i] changes the sum. We need sum = n/2.
            # If we change h[i] from saved to x, the sum changes by (x - saved).
            # We need to compensate... but that breaks the "fix all else" assumption.
            
            # Hmm, this is a problem. The sum constraint couples all coordinates.
            # One approach: ignore the sum constraint in the coordinate step,
            # then re-project after each step or each pass.
            # But re-projecting changes all coordinates, not just h[i].
            
            # Alternative: parameterize as h[i] + c where c is a constant offset
            # applied to all other coordinates to maintain the sum.
            # This gets complicated.
            
            # Simplest: just do the coordinate step ignoring the sum,
            # then project the whole vector.
            
            # Find x that minimizes max_r (s0[r] + x * (s1[r] - s0[r]))
            # This is a 1D problem: minimize the max of m lines.
            
            # The optimal x is where the upper envelope is minimized.
            # We can find it by: the upper envelope is the max of m lines.
            # Its minimum is at a point where two (or more) lines are tied for the max.
            
            # Algorithm: 
            # 1. Evaluate the upper envelope at x=0: value = max(s0)
            # 2. Evaluate at x=1: value = max(s1)
            # 3. Find all breakpoints (intersections of pairs of lines that are on the upper envelope)
            # 4. Check the envelope value at each breakpoint and at 0, 1
            # 5. Return the x with the minimum value
            
            # For efficiency, we can use the fact that the upper envelope of m lines
            # can be computed in O(m log m) using a convex hull trick, or O(m²) naively.
            # For m=127, O(m²) = 16129 is fine.
            
            best_x = saved
            best_val = _exact_c5(h)
            
            # Check x = 0 and x = 1
            for test_x in [0.0, 1.0]:
                h[i] = test_x
                val = max(s0 + test_x * (s1 - s0))
                if val < best_val:
                    best_val = val
                    best_x = test_x
                h[i] = saved
            
            # Find breakpoints: for each pair (r1, r2), the intersection is at
            # x = (s0[r2] - s0[r1]) / (s1[r1] - s1[r2]) if denominator != 0
            # But we only care about breakpoints where both lines are on the upper envelope.
            # Simpler: just check all pairwise intersections in [0, 1].
            
            # Actually, even simpler: the minimum of the upper envelope is either
            # at x=0, x=1, or at a point where two lines cross AND both are
            # simultaneously the maximum. We can find this by:
            # For each x in {0, 1} and at each intersection point, evaluate the envelope.
            
            # But O(m²) intersections is 16129, each requiring O(m) to evaluate = O(m³) = 2M.
            # That's too slow per coordinate.
            
            # Better approach: binary search on the answer.
            # The minimum value v* satisfies: there exists x such that all s_r(x) ≤ v*.
            # s_r(x) = s0[r] + x*(s1[r]-s0[r]) ≤ v*
            # => x ≤ (v* - s0[r]) / (s1[r] - s0[r]) if s1[r] > s0[r]
            # => x ≥ (v* - s0[r]) / (s1[r] - s0[r]) if s1[r] < s0[r]
            # => v* ≥ s0[r] if s1[r] = s0[r]
            
            # So for a given v*, the feasible x range is:
            # x ∈ [max_{r: s1[r]<s0[r]} (v*-s0[r])/(s1[r]-s0[r]), 
            #         min_{r: s1[r]>s0[r]} (v*-s0[r])/(s1[r]-s0[r])]
            # intersected with [0, 1]
            
            # We want the smallest v* such that this range is non-empty.
            # This is a 1D feasibility problem that can be solved by binary search on v*.
            
            # Let me implement this:
            
            def _feasible(v):
                # Check if there exists x in [0,1] such that all s_r(x) <= v
                lo_x = 0.0
                hi_x = 1.0
                for r in range(m):
                    slope = s1[r] - s0[r]
                    if abs(slope) < 1e-15:
                        if s0[r] > v + 1e-15:
                            return False
                    elif slope > 0:
                        # s_r(x) <= v => x <= (v - s0[r]) / slope
                        hi_x = min(hi_x, (v - s0[r]) / slope)
                    else:
                        # s_r(x) <= v => x >= (v - s0[r]) / slope
                        lo_x = max(lo_x, (v - s0[r]) / slope)
                return lo_x <= hi_x + 1e-15
            
            # Binary search on v*
            lo_v = max(s0.min(), s1.min())  # lower bound on v*
            hi_v = max(s0.max(), s1.max())  # upper bound
            # Actually, lo_v should be max over r of min(s0[r], s1[r])
            # because at x=0 the value is s0[r], at x=1 it's s1[r], and in between it's linear
            lo_v = float(np.maximum(s0, s1).min())  # Hmm, not quite right
            # The minimum possible max is at least max over r of min(s0[r], s1[r])
            # because s_r(x) >= min(s0[r], s1[r]) for all x in [0,1]
            lo_v = float(np.minimum(s0, s1).max())
            hi_v = float(np.maximum(s0, s1).max())
            
            for _ in range(50):
                mid_v = (lo_v + hi_v) / 2.0
                if _feasible(mid_v):
                    hi_v = mid_v
                else:
                    lo_v = mid_v
            
            v_star = hi_v
            # Now find the x that achieves v_star
            lo_x = 0.0
            hi_x = 1.0
            for r in range(m):
                slope = s1[r] - s0[r]
                if abs(slope) < 1e-15:
                    continue
                elif slope > 0:
                    hi_x = min(hi_x, (v_star - s0[r]) / slope)
                else:
                    lo_x = max(lo_x, (v_star - s0[r]) / slope)
            
            opt_x = (lo_x + hi_x) / 2.0
            opt_x = max(0.0, min(1.0, opt_x))
            
            h[i] = opt_x
            h = _project(h, n / 2.0)
            
            new_c5 = _exact_c5(h)
            if new_c5 < best_c5:
                best_c5 = new_c5
    
    return h, best_c5

Wait, there's an issue. When I set h[i] = 0 and h[i] = 1 to compute s0 and s1, the sum constraint is violated. But I'm only using s0 and s1 to determine the optimal direction, and then I project back. The issue is that the optimal h[i] might not be the same after projection.

Actually, let me reconsider. The scores s_r = Σ h[j]*(1-h[j+d]) don't directly depend on the sum constraint. The sum constraint is just a feasibility constraint on h. So when I compute s0 and s1, they're the scores at those points regardless of feasibility. The optimal h[i] (ignoring the sum) is what I compute. Then I project back to satisfy the sum.

But the projection might undo the improvement. For example, if the optimal h[i] is 0.5 but the projection forces it to 0.3, the actual improvement might be less.

A better approach: incorporate the sum constraint directly. When I change h[i] from its current value to x, the sum changes by (x - h[i]). To maintain the sum, I need to distribute this change among the other coordinates. The simplest way is to add a uniform offset: each other coordinate gets an adjustment of -(x - h[i]) / (n-1).

But this changes all the scores, not just the ones involving h[i]. So the analysis becomes more complex.

Alternative: just do the coordinate step without the sum constraint, then project. The projection is a small perturbation if the step is small. Over many passes, this should converge.

Actually, let me think about this differently. The projection `_project(v, target)` clips and shifts to achieve the target sum. If v is already close to the constraint set (which it should be after the first pass), the projection is a small perturbation. So the coordinate descent should still make progress.

Let me also consider: maybe I should do the coordinate step WITH the sum constraint by parameterizing properly.

If I change h[i] to x, and distribute the excess (x - h[i])_old as a uniform offset to all other coordinates:
h[j]_new = h[j]_old - (x - h[i]_old) / (n-1) for j ≠ i

Then the score s_r changes by:
Δs_r = (terms involving h[i]) + (terms involving the offset in other h's)

This is more complex but doable. However, for simplicity, let me just use the projection approach.

Let me also think about the efficiency. For each coordinate i:
1. Set h[i] = 0, compute scores: O(n²) for the correlate
2. Set h[i] = 1, compute scores: O(n²)
3. Binary search on v*: 50 iterations × O(m) = O(50m)
4. Find optimal x: O(m)
5. Project: O(n log n) for the bisection

Total per coordinate: O(n²) ≈ O(4096) for n=64
Total per pass: O(n³) ≈ O(262144)
For 100 passes: O(2.6 × 10^7) - very fast!

This is much faster than the LP approach. And it's exact (each coordinate step is optimal).
