```python
    n = len(v)
    if target <= 0: return np.zeros(n)
    if target >= n: return np.ones(n)
    lo, hi = float(v.min()) - 2.0, float(v.max()) + 2.0
    for _ in range(60):

        s = float(np.sum(np.clip(v - mid, 0.0, 1.0)))
        if s > target: lo = mid
        else: hi = mid

            # So c = 1 - h[i-d] - h[i+d] (with zeros for out of range)  ✓
            
            # Now solve: min_t max_d (scores[d] + t * c[d]) for t in [t_min, t_max]
            t_min = max(-h[i], 0.0 - h[i])  # x = h[i] + t >= 0 → t >= -h[i]
            # Wait, t = x_new - x_old = x_new - h[i]
            # x_new >= 0 → t >= -h[i]
            # x_new <= 1 → t <= 1 - h[i]
            t_lo = -h[i]
            t_hi = 1.0 - h[i]
            
            t_opt, _ = _coord_1d_lp(scores, c, t_lo, t_hi)
            h[i] += t_opt
            
            # Update scores incrementally
            delta = t_opt
            if abs(delta) > 1e-15:
                scores += delta * c
    
    # Project to ensure feasibility
    h = _project(h, target)
    return h
```

Wait, there's a subtlety. When I update h[i], the scores change, but I'm using the old scores to compute c. The c values depend on h[i-d] and h[i+d], which don't change when I update h[i] (only h[i] changes). So c is correct for the current update.

But after the update, scores should be updated. The update is:
scores_d_new = scores_d_old + delta * c_d

where c_d = 1 - h[i-d] - h[i+d] (with the old h[i-d] and h[i+d], which are unchanged).

This is correct! Because:
scores_d = sum_j h[j+d]*(1-h[j])
After changing h[i] from x_old to x_new = x_old + delta:
- If i+d is a valid j (i.e., the term h[i+d]*(1-h[i]) exists): change is -delta * h[i+d]
- If i is a valid j+d (i.e., the term h[i]*(1-h[i-d]) exists): change is delta * (1-h[i-d])

So total change = delta * (1-h[i-d]) - delta * h[i+d] = delta * (1 - h[i-d] - h[i+d]) = delta * c_d ✓

Great, so the incremental update is correct.

Now, there's another subtlety: after the coordinate descent sweep, h might not exactly satisfy the sum constraint (due to floating point). We should project at the end.

But actually, each coordinate update preserves the sum! Because we're changing h[i] by t_opt, and the sum constraint is sum(h) = n/2. If we start with sum(h) = n/2 and change h[i] by delta, the new sum is n/2 + delta. That's NOT preserving the sum!

Oh wait, I made an error. The constraint is sum(h) = n/2. If I change h[i] by delta, the sum changes by delta. So I need to either:
1. Add the sum constraint to the 1D LP (making it: minimize max_d (a_d + t*c_d) subject to sum(h) + t = n/2, i.e., t = 0... wait that means t must be 0!)

Hmm, that's a problem. If the constraint is exactly sum(h) = n/2, then we can't change any single coordinate without violating the constraint.

The solution is to use **paired coordinate updates**: change h[i] by +t and h[j] by -t (or some combination) to preserve the sum.

Or: use a Lagrange multiplier for the sum constraint and optimize the Lagrangian.

Or: use a "relaxed" approach where we allow the sum to drift slightly and project at the end of each sweep.

I think the cleanest approach is **paired updates**:
- Update h[i] by +t and h[j] by -t simultaneously
- This is a 2D LP: minimize max_d (a_d + t*c_d^i - t*c_d^j) = min_t max_d (a_d + t*(c_d^i - c_d^j))
- This is still a 1D LP! (since it's a function of a single parameter t)

The slopes become: c'_d = c_d^i - c_d^j
where c_d^i = 1 - h[i-d] - h[i+d] and c_d^j = 1 - h[j-d] - h[j+d]

So c'_d = (1 - h[i-d] - h[i+d]) - (1 - h[j-d] - h[j+d]) = h[j-d] + h[j+d] - h[i-d] - h[i+d]

And the feasible range for t:
- h[i] + t >= 0 and h[i] + t <= 1 → -h[i] <= t <= 1-h[i]
- h[j] - t >= 0 and h[j] - t <= 1 → h[j]-1 <= t <= h[j]

Combined: max(-h[i], h[j]-1) <= t <= min(1-h[i], h[j])

This is clean and preserves the sum constraint exactly!

Let me redesign the algorithm around paired updates:

```python
def _paired_update(h, scores, i, j):
    """Update h[i] += t, h[j] -= t to minimize max score."""
    n = len(h)
    d_vals = np.arange(2*n-1) - (n-1)
    
    # c for coordinate i: c^i_d = 1 - h[i-d] - h[i+d]
    # c for coordinate j: c^j_d = 1 - h[j-d] - h[j+d]
    # Combined slope: c'_d = c^i_d - c^j_d = h[j-d] + h[j+d] - h[i-d] - h[i+d]
    
    idx = d_vals  # d values from -(n-1) to n-1
    
    # h[i+d], h[i-d], h[j+d], h[j-d]
    hp_i = i + idx; valid_p_i = (hp_i >= 0) & (hp_i < n)
    hm_i = i - idx; valid_m_i = (hm_i >= 0) & (hm_i < n)
    hp_j = j + idx; valid_p_j = (hp_j >= 0) & (hp_j < n)
    hm_j = j - idx; valid_m_j = (hm_j >= 0) & (hm_j < n)
    
    cp = np.zeros(2*n-1)
    cp[valid_p_i] += h[hp_i[valid_p_i]]
    cp[valid_m_i] += h[hm_i[valid_m_i]]
    cp[valid_p_j] -= h[hp_j[valid_p_j]]
    cp[valid_m_j] -= h[hm_j[valid_m_j]]
    # cp = h[j-d] + h[j+d] - h[i-d] - h[i+d]
    
    # Feasible range
    t_lo = max(-h[i], h[j] - 1.0)
    t_hi = min(1.0 - h[i], h[j])
    
    if t_hi - t_lo < 1e-15:
        return 0.0
    
    t_opt, _ = _coord_1d_lp(scores, cp, t_lo, t_hi)
    
    # Apply update
    h[i] += t_opt
    h[j] -= t_opt
    scores += t_opt * cp
    
    return t_opt
```

This is clean and efficient. The 1D LP is the same as before, just with different slopes.

Now, for the overall algorithm:
1. Start with initial h (from initial_h_values)
2. Compute scores
3. Do many paired updates (random i, j pairs)
4. Project to ensure feasibility (should be exact if we started feasible)
5. Repeat with different random seeds
6. Return best

But wait, there's a problem with the coordinate descent approach: it will tend to push values to 0 or 1 (binary). The 1D LP will often have its optimum at the boundary (t = t_lo or t = t_hi). This is fine for finding binary solutions, but the optimal solution might be non-binary.

To handle non-binary optima, I should also do **single-coordinate updates with a Lagrange multiplier** for the sum constraint, or use **paired updates where the pair (i,j) is chosen to allow non-trivial t**.

Actually, the paired update already handles this: if the optimal t is interior (not at the boundary), then both h[i] and h[j] will be non-binary. This happens when the interior minimum of the 1D LP is in the feasible range.

Let me also add **block updates of size 2**: update h[i] by +t1 and h[j] by +t2, with t1 + t2 = 0 (to preserve sum). This is the same as the paired update above.

For updates of size 3: h[i] by +t1, h[j] by +t2, h[k] by -(t1+t2). This is a 2D LP. I'll skip this for now and focus on paired updates.

One more thought: the 1D LP solver `_coord_1d_lp` is the bottleneck. Let me make sure it's efficient.

For K = 2n-1 ≈ 311:
- The O(K²) approach: 311² ≈ 97,000 pairwise intersections
- Each intersection: 2 subtractions, 1 division, 2 comparisons
- Then filter and evaluate: O(K) per candidate

In numpy, this should be fast. Let me estimate:
- Creating the K×K difference arrays: ~100μs
- Division and filtering: ~50μs
- Evaluating at candidates: depends on number of valid candidates

In the worst case, all ~97,000 candidates are valid, and evaluating f at each is O(K) = 311. Total: 97,000 * 311 = 30 million operations. In numpy, this is about 30ms. That's too slow for a Python loop.

Let me optimize: instead of evaluating f at all candidates, I can:
1. Check endpoints first (O(K) each)
2. If endpoint is optimal, done
3. Otherwise, use a more efficient method to find the interior minimum

For the interior minimum, I can use the fact that the upper envelope is convex. The minimum is where the subdifferential contains 0, i.e., where there's a point with active lines having both positive and negative slopes (or a single active line with slope 0).

A more efficient approach:
1. Sort the lines by slope
2. Use the convex hull trick to find the upper envelope in O(K log K)
3. Binary search on the upper envelope to find where the slope crosses 0
4. Check if this point is in [t_min, t_max]
