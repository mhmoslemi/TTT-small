- h[i] appears in the second factor (1-h[n]) when n = i. Valid if 0 ≤ i < n (always true) and 0 ≤ i+offset < n. So: -h[i+offset] * [0 ≤ i+offset < n]

For the pair step, I need to:
1. Compute the current correlations
2. For the pair (i, j), compute how each correlation changes as we vary s = h[i] - h[j]

4. Update

But recomputing correlations from scratch for each pair is O(n²), and we have n/2 pairs per sweep, giving O(n³) per sweep. For n=126, that's about 2M per sweep. With 50 sweeps, that's 100M operations. In numpy this should be fine (each correlate call on a length-126 array is very fast).

Actually, let me think about whether I can avoid recomputing the full correlate for each pair. The change in corr[offset] when I change h[i] and h[j] is:
Δcorr[offset] = Δh[i] * c_i(offset) + Δh[j] * c_j(offset)

where c_i(offset) = (1-h[i-offset])*[valid] - h[i+offset]*[valid] (as derived before).

So I can:
1. Compute corrs once at the start of the sweep
2. For each pair, compute c_i and c_j (O(n) each)
3. Find the optimal s (O(n) for the binary search on the derivative)
4. Update corrs incrementally: corrs += Δh[i]*c_i + Δh[j]*c_j

This gives O(n) per pair step (for computing c_i, c_j, and the binary search), plus O(n) for the incremental update. Total per sweep: O(n²). Much better!

But wait, c_i and c_j depend on the current h, which changes as we go through the pairs. So the incremental update is only approximately correct (since c_i was computed with the old h). For a single sweep, this is like a Gauss-Seidel update, which should converge.

Actually, for exactness, I should recompute c_i and c_j at each step (using the current h). Since they're O(n) to compute, this is fine.
