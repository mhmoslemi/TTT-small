Let me also think about the "shift-informed" move generation more carefully:

For shift k, the bad pairs are {(i, i+k) : 0 ≤ i < n-k, h[i]=1, h[i+k]=0}.
A swap that moves h from position i to position i+k fixes this bad pair.
But it also:
- Makes position i a 0 (which might create new bad pairs for other shifts)
- Makes position i+k a 1 (which might fix or create bad pairs for other shifts)

The net effect on c_k for the same shift k:
- The pair (i, i+k) is fixed: c_k decreases by 1
- But new pairs might be created: if there exists i' such that h[i']=1 and i'+k = i (i.e., i' = i-k), then the pair (i', i) was h[i-k]=1, h[i]=1 (good), but now h[i]=0, so it becomes (i', i) = (1, 0) which is bad. Similarly, if i+k+k is in range and h[i+2k]=0, then pair (i+k, i+2k) was (0, 0) but becomes (1, 0) which is bad.

So a single swap at shift k can fix one bad pair but create up to 2 new bad pairs at the same shift. The net change in c_k is: -1 + (new bad pairs created).

This is why simple greedy can get stuck - it fixes one pair but creates others.

The 2-swap helps because you can fix two bad pairs simultaneously while managing the side effects.
