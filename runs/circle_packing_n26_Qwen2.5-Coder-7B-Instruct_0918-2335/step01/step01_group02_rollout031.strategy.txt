**Goal**

Locate a planting of 26 circles inside the unit square that maximises the total length of radius.  
Current best objectively‑optimised packing (SLSQP with random starts) gives a sum of radii  
≈ 2.608.  The target is 2.636, a margin of ≈ 1 % which is usually very difficult to gain with a plain local optimiser because the feasible set is non‑convex and the optimum sits on a highly constricted part of the boundary.

**Core Idea**

Treat the *positions* of the centres as variables, and for any fixed set of positions compute the *maximum feasible radii* by solving a linear programme.  
The objective – the sum of radii – becomes a *piecewise‑linear concave* function of the positions.  
A black‑box optimiser that only evaluates this function (but never cooperates with gradients) can sharply explore the region around the optimum.  The optimiser of choice is `scipy.optimize.differential_evolution` because

* it is global (population based, not stuck in a local optimum)  
* it only needs the objective value  
* it can handle high‑dimensional searches (52 variables: 26×2 coordinates) within a reasonable amount of time when the objective is inexpensive.

Once the DE has located a promising region we polish the solution with a fast local optimiser (SLSQP) that now optimises *both* positions *and* radii together.  This last step guarantees that the radii given by the LP are not artefacts of the fixed positions but lie genuinely on the non‑linear feasible manifold.

**Detailed Steps**

1. **Linear Program for Radii (fixed positions)**  
   *Variables* : 26 real radii \(r_i\).  
   *Constraints*  
   * Bound to the square:  
     \[
     r_i \le x_i,\qquad r_i \le 1-x_i,\qquad   
     r_i \le y_i,\qquad r_i \le 1-y_i
     \]
   * Non‑overlap:  
     \[
     r_i+r_j \le d_{ij}\ \forall\, i<j
     \]
     where \(d_{ij}\) is the Euclidean distance between the chosen centre positions.
   * Radii non‑negative: \(r_i\ge0\).  
   *Objective* : maximise \(\sum_i r_i\); implemented as minimising \(-\sum_i r_i\).

   Every feasible set of positions guarantees feasibility of this LP because \(r_i=0\) satisfies all inequalities, thus the solver is never asked to solve an infeasible problem.

2. **Fitness Function for DE**  
   *Input* : 52‑dimensional vector \((x_1,y_1,\dots,x_{26},y_{26})\).  
   *Process* :  
   - Compute all pairwise distances.  
   - Assemble `A_ub` and `b_ub` for the LP.  
   - Call `scipy.optimize.linprog(method='highs')`.  
   - Return the *negative* of the optimum sum of radii as the objective value (DE minimises).  
   *Output* : scalar value used by DE; the returned radii can be stored for later use.

3. **Differential Evolution Run**  
   *Bounds* : all coordinates in \([0,1]\).  
   *Population size* : 50 (area: 52×50 = 2600 individuals).  
   *Iterations* : 200 (results in ~520 k LP solves).  
   *Random seed* : a fixed seed (e.g. 42) to keep the run deterministic.  
   *Stopping criterion* : either the algorithm finishes its iterations or a timeout is detected.

**Why This Works**

* The linear programme is the convex hull of all radius configurations for the given centres.  Therefore the optimum LP radius vector is the true maximum that can be attained for these centres.  
* The sum of radii is, for each position, exactly the optimal value returned by the LP, so the DE objective exactly mirrors the true global objective over the manifold of positions.  
* The global search (DE) is able to push through the highly non‑convex landscape and chase the subtle dependencies that give rise to a larger total radius; at the same time the convex radii sub‑problem guarantees that the search never takes a step that would unwise–ly over‑tilt the radii.  
* The SLSQP refinement operates on the full nonlinear manifold and usually finds a slightly higher local optimum within the DE‑identified basin because the LP step fixes the radii at the value that is optimal *for the current positions*, but does not allow positions to adapt to the radii; local re‑optimisation can slightly adjust both.

**Numerical Settings**

* All coordinates and radii are stored in double precision (`np.float64`).  
* `linprog(..., method='highs')` has negligible CPU time compared to the distance matrix generation.  
* A tolerance of `1e-12` for constraints is stricter than the validator (`1e-10`), ensuring that no small numerical violation sneaks through.
