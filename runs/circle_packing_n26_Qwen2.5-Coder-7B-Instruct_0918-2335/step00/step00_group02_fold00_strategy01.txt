**Overall idea**

The sum of radii is maximised *if, for any fixed set of circle centres, the radii are chosen as large as the geometry allows*.  
Consequently we can separate the problem into two levels:

| Level | Variables | Constraints | Optimisation |
|-------|-----------|-------------|--------------|
| **Inner** | Radii \(r_{1}\ldots r_{26}\) | 1) \(0\le r_{i}\le \min(x_i,\,1-x_i,\,y_i,\,1-y_i)\)  
2) \(r_{i}+r_{j}\le d_{ij}\) for every pair of centres | Ordinary linear program – maximum‑sum‑objective |
| **Outer** | Circle centres \((x_i,y_i)\) | \(0\le x_i,y_i\le1\) | Global optimisation in 52‑dimensional space (no explicit radius variables) |

The **inner LP** guarantees that, for the current configuration of centres, the radii are optimal.  
The **outer optimiser** now only has to use the maximal attainable radii as a reward signal.  
This is fundamentally different from the previous “continuous optimisation of both centres and radii”, because the radii are never guessed; they are *exactly* induced by the geometry.  
The consequence is that the outer optimiser is no longer responsible for handling overlap or boundary violations – those are dealt with exactly inside the LP – and that the objective function becomes a *piecewise‑linear concave* function of the centres, which is easier for derivative‑free optimisers to navigate.

### 1. Constructing the inner linear programme

For a given configuration of centres (`centres[i] = (x_i, y_i)`) we perform:

1. **Boundary limits**  
   \[
   b_i = \min\{x_i, 1-x_i,\, y_i, 1-y_i\}
   \]
   This is the largest radius a circle centered at \((x_i,y_i)\) can have without touching the square boundary.

2. **Inter‑circle distances**  
   \[
   d_{ij} = \|\,\text{centres}[i]-\text{centres}[j]\,\|_{2}
   \]
   (computed once per evaluation).

3. **LP specification**  
   *Variables*: `r` – a 26‑vector of radii.  
   *Objective*: maximise \(\sum r_i\) → minimise \(-\sum r_i\).  
   *Inequalities*:
   * \(r_i \le b_i\)  (28 inequalities)
   * \(r_i \ge 0\) ↔ \(-r_i \le 0\)  (26 inequalities)
   * \(r_i + r_j \le d_{ij}\) for all \(i<j\)  (325 inequalities)

All constraints are linear; we solve with SciPy’s `linprog` (method `highs`).  
Because all right‑hand sides are non‑negative and because we always set an upper bound on \(r_i\) (the boundary limit), the LP is always feasible (the trivial solution \(r_i=0\) is admissible).  
The solver returns the optimum radii and their sum \(S\); that sum is the **reward** for the outer optimisation.

### 2. Outer optimisation with Differential Evolution

**Variables**  
A flat array of 52 elements: `[x_0, y_0, x_1, y_1, …, x_{25}, y_{25}]`.  
Bounds: all coordinates in \([0,1]\).

**Population & run parameters**

| Parameter | Typical value | Rationale |
|-----------|---------------|-----------|
| `popsize` | 48 (≈ 2 × dim) | Gives diverse initial seeds while staying fast. |
| `maxiter` | 200 | Roughly 9 500 LP evaluations – well below 1 min on a single core. |
| `tol` | 1e‑6 | Stop early if objective has converged. |
| `seed` | 42 (single run) | Deterministic, but we keep the ability to run a few restarts if needed. |

**Evaluation function**

For each candidate centre vector:

1. Reshape into `(26,2)`.
2. Compute the 26 × 26 distance matrix with full vectorised NumPy operations – `dx = xs[:,None]-xs[None,:]`, `dy = ys[:,None]-ys[None,:]`, `dist = np.hypot(dx,dy)`.
3. Build the LP matrices `A_ub` and `b_ub` as described above.
4. Call `linprog`.  
   *If the solver fails* (unlikely but safe to guard), return a very large negative reward (`-1e6`), so DE ignores that candidate.
5. Otherwise, compute the sum of radii `S = r.sum()` and return the **negative** of `S` as the fitness value (`-S`).  DE always minimises, so it will drive the system toward larger sums.

**Why DE?**  
The 52‑dimensional search manifold is highly non‑convex with many local optima (different permutations of circles, contact graphs, etc.).  Differential evolution has a proven track record on such global optimisation problems, uses only bounds, and is straightforward to implement with SciPy.  Since the inner objective can be evaluated in a few milliseconds, its repeated calls are acceptable.

### 3. Optional local polishing

Because DE may stop at a moderately good but not optimal configuration, we add a lightweight local search:

1. Take the best centre set from DE.
2. Run a limited number of local random perturbations (e.g. 50 iterations).  
   Each iteration:
   * Perturb each coordinate by a Gaussian noise with a *shrinking* standard deviation (start at 0.01, reduce to 1e‑4).
   * Evaluate reward via the inner LP as above.
   * Accept if reward increases; otherwise keep previous centre set.
3. The perturbations are cheap (they trigger one LP per trial), and they can push the configuration over small basins of attraction that DE missed.

### 4. Post‑processing and validation

1. After polishing, solve the LP one last time to obtain the final radii vector.
2. Round the radii to 12 decimal places to avoid tiny negative values produced by numerical noise.
3. Assemble `centres` as an array of shape `(26,2)` and `radii` as shape `(26,)`.
4. Compute `sum_radii = radii.sum()`.
5. Optional: run the supplied `validate_packing` to be absolutely certain of feasibility (must pass otherwise we raise an exception).  

Return `(centres, radii, sum_radii)`.

### 5. Implementation notes

* **NumPy vectorisation** – all distance calculations and LP matrix assembly are fully vectorised; there is no Python‑loop over pairs, which keeps evaluation fast.
* **Scipy constants** – we use `scipy.optimize.linprog` with `method='highs'`, which is the latest, fast, and robust solver in SciPy when dealing with moderate numbers of variables/constraints.
* **Determinism** – The random seed (`np.random.seed(42)`) ensures reproducibility; the only source of nondeterminism is the DE algorithm itself, but with a fixed seed the outcome is identical across runs.
* **Failure handling** – If the LP solver returns `status != 0`, we treat the candidate as unusable. This can happen for pathological centre sets where numerical errors cause infeasibility; throwing the candidate away is safe because the objective `-1e6` makes DE discard it.
* **Computational effort** – Each DP evaluation is ≈ 0.5 ms on a recent CPU. With 9 500 evaluations (~0.5 s) plus polishing (~0.1 s), the whole process finishes well under a second, comfortably within the limit.
