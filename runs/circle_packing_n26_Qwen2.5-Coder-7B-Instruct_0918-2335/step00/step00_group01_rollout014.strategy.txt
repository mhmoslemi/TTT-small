**Goal** – pack 26 non‑overlapping circles into a unit square so that the sum of their radii is as large as possible (target 2.636).  
**Idea** – simulate a *dynamical system of hard circles that grow uniformly over time* (the classical Lubachevsky–Stillinger protocol). When no further growth is possible, the radii are maximal for the given centre layout.  The final configuration is then *polished* with a linear programme that maximises the radii for that fixed geometry.  

This approach is fundamentally different from the previous LP‑dual, evolutionary or purely force‑directed schemes: it uses an *event‑driven continuous‑time simulation* of expanding hard discs, not a static optimisation of a pre‑chosen contact graph.

--------------------------------------------------------------------
### 1.  Mathematical model

We model each circle \(i\) by

* centre \(c_i(t) = (x_i(t),y_i(t))\)
* radius \(r_i(t)\)
* velocity vector \(v_i\) (constant between collisions).

All circles start very small, \(r_i(0)=r_{\min}=10^{-4}\).  
All radii grow at the same constant rate \(g>0\) :  
\( \displaystyle \frac{dr_i}{dt}=g\).

The dynamics is constrained by two sets of equations:

1. **Non‑overlap** – for any pair \(i<j\):  
   \[
   \|c_i(t)-c_j(t)\|\;\ge\; r_i(t)+r_j(t)
   \]
2. **Boundary enclosure** – for all \(i\):  
   \[
   r_i(t)\;\le\;\min(x_i(t),1-x_i(t),y_i(t),1-y_i(t))
   \]

When a constraint becomes active the circles undergo an *elastic collision*:

* If circles \(i\) and \(j\) touch, their relative velocity along the line of centres is reflected, conserving kinetic energy and momentum:
  \[
  v_i' = v_i - \frac{2\,m_j}{m_i+m_j}\,\frac{\langle v_i-v_j ,c_i-c_j\rangle}{\|c_i-c_j\|^2}\,(c_i-c_j)
  \]
  (all masses \(m_i\) are set to 1; the expression simplifies to a simple reflection of the normal component).  

* If a circle hits a boundary plane \(x=0\) or \(x=1\) (similarly \(y\)), its velocity component normal to that wall is negated (bounce).

Essentially we evolve the system in discrete *events*: each event is either a *collision* between two circles or a *collision* with a wall. Between events, circles move linearly (with their velocity) while their radii increase linearly.

--------------------------------------------------------------------
### 2.  Event detection

For every *potential* pair we compute the *earliest* future time \(t>0\) at which the constraint becomes active:

* **Circle–circle pair \(i,j\)**  
  Let  
  \[
  \Delta c_0 = c_i(0)-c_j(0),\quad
  \Delta v = v_i-v_j,\quad
  \Delta r_0 = r_i(0)+r_j(0),\quad
  g_{\!tot}=2g.
  \]
  We need \(t\) solving  
  \[
  \|\Delta c_0+\Delta v\,t\| = \Delta r_0 + g_{\!tot}\,t .
  \]
  Squaring and rearranging gives a quadratic
  \[
  \|\Delta v\|^2 t^2 + 2\langle\Delta c_0,\Delta v\rangle t + \|\Delta c_0\|^2
  = (\Delta r_0 + g_{\!tot}\,t)^2 .
  \]
  Solving this quadratic yields the smallest positive root \(t_{\!cc}\).  
  If \(t_{\!cc}\) is negative or does not exist → no upcoming collision.

* **Circle–wall pair**  
  For the left wall \(x=0\), let \(x_i(t)=x_i(0)+v_{i,x}t\).  
  Solve \(x_i(t)-r_i(t)=0\):  
  \(x_i(0)+v_{i,x}t = r_{\min}+g\,t\).  
  The solution \(t_{\!cw}\) is simply  
  \[
  t_{\!cw} = \frac{r_{\min}-x_i(0)}{v_{i,x}-g},
  \]
  provided \(v_{i,x}-g<0\).  
  Analogous formulas hold for the other three walls.

All upcoming events (pairwise and wall) are inserted into a **priority queue** (min‑heap keyed by event time).  The queue always contains the soonest event.

--------------------------------------------------------------------
### 3.  Simulation loop

```
initialise positions c_i(0) randomly in the square
initialise radii r_i(0)=r_min
initialise random unit velocities v_i  (choose a small speed, e.g. 0.01)
build initial event queue
current_time = 0

while event queue not empty and current_time < T_max:
    pop the event with smallest time t_e
    advance all circles by Δt = t_e - current_time:
        c_i += v_i * Δt
        r_i += g * Δt
    current_time = t_e
    resolve the event:
        if event is circle–circle:
            reflect velocities v_i, v_j as above
        else (circle–wall):
            flip appropriate velocity component
    recompute events involving the affected circles:
        delete obsolete entries from queue
        compute new collision times with other circles and walls
        push those events into the queue
```

*Termination*:  
The simulation stops when the priority queue is empty (no future collisions) or when a predetermined time limit \(T_{\max}\) is reached.  In practice, for 26 circles the queue empties after a few dozen events: the system has become *jammed* and further growth would force a collision that cannot be resolved without overlap.  The radii at that instant are the maximal radii for that set of centres.

--------------------------------------------------------------------
### 4.  Feasibility correction

Because of floating‑point inaccuracies, the final configuration might contain tiny overlaps or slight boundary violations.  We therefore:

1. **Shrink all radii** by a small epsilon \(\varepsilon = 10^{-6}\).  
2. **Run a quick repair**: if any overlaps remain (detected by the validator’s `validate_packing`), perform a tiny repulsive step: for each overlapping pair \((i,j)\) move the two centres apart along the line of centres by a distance proportional to the overlap and regenerate the radii.  
   This repair is very cheap because the number of violations, if any, is tiny.

After this correction the configuration is strictly feasible and ready for the final polish.

--------------------------------------------------------------------
### 5.  LP polish – exact radii for the attained centres

With the final set of centres fixed, we solve the linear program described in Section 1:

* Variables: radii \(r_i\).  
* Objective: maximize \(\sum r_i\).  
* Constraints: the four boundary inequalities and all \(n(n-1)/2\) pairwise inequality constraints.

Using `scipy.optimize.linprog` with the `'highs'` method, the LP is solved in a few milliseconds and guarantees the **maximum possible sum of radii** for the given geometry.  This final step compensates for any shrinkage during the repair stage and ensures that no subtle improvement is missed.

### 7.  Failure mechanisms and mitigations

| Failure mode | Why it can happen | Mitigation |
|--------------|-------------------|------------|
| **Unresolved collisions** – the priority queue empties before radii can grow enough, leading to sub‑optimal packing | If the initial velocities are too small or all circles start very close | Use a moderate velocity magnitude and add a small random jitter to positions to avoid pathological initial configurations. |
| **Floating‑point drift** – tiny overlaps after the simulation | Event times are computed numerically; the system is not perfectly jammed | Shrink radii by \(\varepsilon\) and run a one‑pass overlap repair; finally re‑solve the LP to guarantee optimality. |
| **Overflow of event times** – unrealistic large Δt because some pair never collides | The quadratic for circle–circle may have no positive root if circles move towards each other slower than the relative growth | Filter out negative or NaN solvers; if no root exists, simply skip that pair. |
| **Slow convergence** – many events, high CPU time | Small growth rate makes many incremental events | Increase \(g\) slightly or allow a maximum event count; after a certain number of events, force a jump step (scale all radii by a factor). |
| **Rubber‑band effects** – circles keep bouncing forever (no jam) | Very high initial velocities can create a low‑density configuration that never jams | Bound the initial speed and, after a preset number of events, apply a damping factor to velocities. |

The event‑driven simulation is algorithmically robust: each event strictly reduces the available free volume, guaranteeing that the queue will eventually empty or the stopping criterion will be met.

* **Number of events** – Empirically, a jammed configuration with 26 circles is reached after 30–100 events; some runs may hit 150 events if the initial velocities are large.  
* **Runtime** – Even a very conservative implementation runs in **< 0.2 s** on a single CPU.  
* **Memory** – the event queue holds at most \(O(n^2)\) entries (< 400).
