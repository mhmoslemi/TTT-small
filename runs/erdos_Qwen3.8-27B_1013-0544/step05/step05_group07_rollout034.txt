                # Recompute C after projection (expensive but necessary for correctness)
                C = np.correlate(h, 1.0-h, mode='full') * dx
        
        c_new = np.max(C)
        if c_new < best_c:
            best_c = c_new
            best_h = h.copy()

Wait, there's a problem: after projecting (which changes multiple coordinates), the incremental C update is no longer valid. I need to recompute C from scratch after projection.

This is expensive (O(n²) per projection). If I project after every coordinate update, that's O(n³) per full cycle, which is too slow.

Alternative: don't project after every update, but after a full cycle. The sum constraint will be approximately maintained if the changes are small.

def coord_descent(h, n, time_budget, max_passes=100):

Hmm, but this still has the issue that the incremental C update might accumulate errors, and the projection at the end of each pass ruins the incremental update.

Let me think of a cleaner approach:

**Approach: Full recompute but efficient**

Since n=250, np.correlate takes O(n²) = 62500 operations, which is fast with NumPy (probably < 1ms). So even if I recompute C after every coordinate update, a full cycle takes 250 * (1ms + optimization time) ≈ 250 * 2ms ≈ 0.5 seconds.

Let me just recompute C from scratch after each coordinate update. It's simpler and correct.

Actually, let me benchmark: np.correlate of two length-250 arrays. This is a convolution of size 250 × 250 = 62500 multiply-adds. In NumPy, this should take about 50-100 μs. So 250 updates per cycle = 250 * 100μs = 25ms. Plus the optimization (minimize_scalar takes ~50 evaluations × 100μs each = 5ms per coordinate). Total per cycle: 250 * (100μs + 5ms) ≈ 250 * 5.1ms ≈ 1.3 seconds.

So we can do about 100-200 cycles in 1100 seconds. That's more than enough!

Wait, the minimize_scalar is the bottleneck. Each call evaluates f ~50-100 times, and each evaluation is O(n) = O(499) operations (just a max of 499 values). In NumPy, this is very fast: 499 multiplications + 499 additions + a max = ~2μs. So 100 evaluations = 200μs per coordinate.

Total per coordinate: 100μs (correlate) + 200μs (minimize) = 300μs.
Per cycle: 250 * 300μs = 75ms.
In 1000 seconds: ~13000 cycles. More than enough.

Great, so the algorithm is:
1. For each coordinate i (in some order):
   a. Compute d[m] for all m
   b. Compute a = dx*d, b = C - dx*h[i]*d
   c. Find v* = argmin_{v∈[0,1]} max(a*v + b)
   d. Update h[i] = v*, recompute C
2. Project to feasible set
3. Repeat

The key question is: will this converge to a good solution? Coordinate descent on non-convex problems doesn't always converge to the global optimum, but for this specific problem (which has a relatively simple structure), it should work well, especially when started from a good initial point.

Let me also add some enhancements:
- **Random restarts**: If stuck, perturb the solution and try again
- **Random ordering**: Use a random permutation of coordinates in each pass
- **Lagrange multiplier**: Add a penalty for the sum constraint to the coordinate optimization

Actually, for the Lagrange multiplier approach:
min_v max_m (a_m*v + b_m) + λ*v

This is the max of (quadratic + λv) and (linear + λv = linear) functions. Still the same structure. And λ is updated as:
λ ← λ + η * (sum(h) - n/2)

This should help maintain the sum constraint more gracefully.
