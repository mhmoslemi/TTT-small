**Overview**

The goal is to produce a feasible placement of 26 circles inside the unit square that maximizes the sum of radii.  
Instead of a generic nonlinear‑programming (NLP) refinement of a regular lattice, this plan adopts a **two‑stage constructive‑optimization framework**:

1. **Global layout via a mixed‑integer linear program (MILP) that decides which of a pre‑computed “candidate” circles are active.**  
   - The candidate set consists of many circles with fixed centre positions on a dense grid and with a set of discrete radius levels (e.g. 0.02, 0.04, …, 0.25).  
   - Binary variables select a candidate; linear constraints enforce at most one circle per grid point, a total of 26 selected circles, and pairwise non‑overlap using the “big‑M” linearisation of the Euclidean distance (approximated by a set of rotated‑square (L∞) constraints).  
   - The MILP maximises the sum of the chosen radii.  
   - Because the MILP is linear (apart from integer variables) it can be solved reliably to global optimality for a modest candidate size (≈ 500–800 candidates) with the open‑source CBC solver that ships with SciPy/OR‑Tools.

2. **Local continuous refinement of the selected circles.**  
   - The MILP yields a feasible discrete configuration (centres fixed to grid points, radii limited to the discrete set).  
   - Treat the selected circles as the initial point for a small‑scale nonlinear optimisation that frees the centre coordinates and allows radii to vary continuously, while keeping the circles in the same “neighbourhood ordering” discovered by the MILP (i.e. we keep the same adjacency graph).  
   - This refinement uses a gradient‑based optimizer (trust‑region or SLSQP) with only the **boundary** and **pairwise distance** constraints (now true Euclidean).  
   - Because the initial layout already respects a strict safety margin (the discrete radii are chosen slightly smaller than the allowed distance to neighbours), the continuous optimizer can increase radii and adjust positions without risking violation, converging quickly to a local optimum that is typically close to the global optimum for this problem size.

The two‑stage approach differs fundamentally from the earlier strategy (which started from a uniform hex lattice and performed a direct NLP). It replaces the initial lattice by a *combinatorial global search* over a rich candidate pool, guaranteeing that the best possible discrete configuration (under the chosen discretisation) is found before any continuous polishing. This often yields a higher initial sum of radii and a better final result.

### Stage 1 – Discrete Global Search

**1.1 Candidate generation**  
*Grid*: Choose a uniform square grid of spacing `g = 0.04` (or slightly finer, e.g. 0.03). This yields ≈ (1/g + 1)² ≈ 30 × 30 ≈ 900 grid points.  
*Radius levels*: For each grid point generate circles with radii drawn from a small arithmetic progression, e.g. `R = {0.02, 0.04, 0.06, …, 0.24}` (max radius limited by distance to the square sides at that point).  
*Feasibility prune*: Discard any candidate whose radius would cross a side of the square (i.e. `x < r`, `x > 1‑r`, `y < r`, `y > 1‑r`). The remaining set typically contains ~500–650 candidates.

Each candidate `k` is described by three constants `(x_k, y_k, r_k)`.

**1.2 Variables**  
- Binary variable `z_k ∈ {0,1}` indicating whether candidate `k` is selected.  
- No continuous variables at this stage; centre and radius are fixed.

**1.3 Constraints**

| Constraint | Description | Linear formulation |
|------------|-------------|--------------------|
| **Single circle per grid point** | At most one radius can be chosen for a given grid location. | For each grid point `p`: Σ_{k at p} z_k ≤ 1 |
| **Exactly 26 circles** | Total number of selected candidates must be 26. | Σ_k z_k = 26 |
| **Pairwise non‑overlap (linearised)** | For any two selected circles `i, j` we must have `dist(i,j) ≥ r_i + r_j`. Direct Euclidean distance is non‑linear, so we replace it by a sufficient set of L∞ (axis‑aligned and 45° rotated) constraints:  <br>`|x_i - x_j| + |y_i - y_j| ≥ r_i + r_j` and <br>`|x_i - x_j| - |y_i - y_j| ≥ r_i + r_j` (the latter after rotating coordinates). These are linear after introducing auxiliary continuous variables for the absolute values. | Use auxiliary variables `dx_ij, dy_ij ≥ 0` with constraints:<br>`dx_ij ≥  x_i - x_j` , `dx_ij ≥ -(x_i - x_j)` (similarly for `dy_ij`). Then impose `dx_ij + dy_ij ≥ r_i + r_j` and `dx_ij - dy_ij ≥ r_i + r_j` (the latter after swapping sign). The variables `dx_ij, dy_ij` are continuous and bounded by 1. |
| **Big‑M linking** | The auxiliary `dx_ij, dy_ij` constraints must be active only when both circles are selected. | Add `dx_ij ≤ M * (z_i + z_j)` and same for `dy_ij`, with `M = 1`. If either `z` is 0, the left‑hand side can be forced to 0, making the inequality trivially satisfied. |

All constraints are linear (or can be expressed as linear with the auxiliary variables). The model size:  
- Variables: `|K|` binaries + `O(|K|^2)` continuous (`dx,dy` for each unordered pair). With ≈600 candidates the pair count is ~180 k, still manageable for CBC because each pair only adds 2 continuous vars and 4 constraints.

**1.4 Objective**  
Maximise the total radius sum: `max Σ_k r_k * z_k`. This is linear.

**1.5 Solver**  
Use `scipy.optimize.linprog` with the MILP interface from `pulp` or `ortools.linear_solver`. The open‑source CBC solver (default in OR‑Tools) solves problems of this size within seconds to minutes. The solution yields the set `S = {k | z_k = 1}` of 26 candidates.

**1.6 Output of Stage 1**  
- Centers: `(x_k, y_k)` for each selected `k`.  
- Radii: `r_k` (discrete).  
- Because the L∞ linearisation is a **sufficient** condition (i.e. if it holds, Euclidean non‑overlap definitely holds), the selected circles are guaranteed to be feasible.  
- The discrete radii are deliberately *conservative* (e.g. we could subtract a tiny safety margin `ε = 1e-4` from each to further guarantee separation). The sum of radii from this stage is typically already > 2.5.

### Stage 2 – Continuous Local Optimisation

**2.1 Purpose**  
The discrete stage provides a combinatorial optimum within the discretisation grid. However, the true optimum may improve by:
- Nudging centre positions off the coarse grid,
- Enlarging radii beyond the discrete levels,
- Exploiting leftover slack between circles.

A small‑scale continuous NLP, initialized at the discrete solution, can capture these gains.

**2.2 Variables**  
For each of the 26 circles we now have three continuous variables: `x_i, y_i, r_i`.

**2.3 Constraints (exact Euclidean)**  

1. **Boundary**: `r_i ≤ x_i`, `r_i ≤ 1 - x_i`, `r_i ≤ y_i`, `r_i ≤ 1 - y_i`.  
   These are linear.

2. **Non‑overlap**: For each unordered pair `(i,j)`  
   ` (x_i - x_j)^2 + (y_i - y_j)^2 ≥ (r_i + r_j)^2`.  
   Implemented as a nonlinear inequality `g_ij(z) = (r_i + r_j) - sqrt((x_i - x_j)^2 + (y_i - y_j)^2) ≤ 0`. This is smooth aside from the square‑root; we can also square both sides to avoid the root, but the optimizer (trust‑constr) handles the root fine.

3. **Non‑negativity**: `r_i ≥ 0` (implicitly covered by boundary constraints but we keep explicit lower bounds).

All constraints are the same form as in the earlier strategy, but now the initial point is much closer to a high‑quality region, and the number of variables is modest (78), making the NLP cheap.

**2.4 Objective**  
Maximise `Σ r_i` → minimise `- Σ r_i`.

**2.5 Solver choice**  
`scipy.optimize.minimize` with method `'trust-constr'` works well for problems with many nonlinear constraints and provides robust handling of Jacobians. Provide analytical gradients:

- Gradient of each boundary constraint is trivial.
- Gradient of each pairwise distance constraint: derivative of `dist = sqrt(dx^2+dy^2)` w.r.t. the four variables is `[(dx/dist), (dy/dist), -(dx/dist), -(dy/dist)]` multiplied by the sign of the inequality (since we need ∂g/∂z).

Providing these Jacobians dramatically speeds convergence and improves reliability.

**2.6 Safeguards**

- **Initial safety margin**: Before launching the NLP, shrink every radius by a tiny amount `δ = 1e-5`. This guarantees the starting point is strictly interior to all constraints, avoiding numerical ties.
- **Barrier for distance zero**: If two selected circles are exactly coincident (unlikely due to the L∞ constraints), add a small regularisation `dist = sqrt(dx^2 + dy^2 + 1e-12)` inside the constraint evaluation to keep gradients finite.
- **Constraint violation handling**: After the optimizer finishes, run a very light repair loop:
  * For each circle, set `r_i = min(r_i, x_i, 1-x_i, y_i, 1-y_i)`.
  * For each overlapping pair, compute overlap `o = (r_i + r_j) - dist`. If `o > 0`, reduce both radii by `o/2` (or the whole `o` from the larger radius) and recompute. Iterate ≤ 5 times. Because the optimizer already satisfies constraints up to ~1e‑9, this loop will almost never trigger, but it guarantees validator compliance.

**2.7 Expected improvement**  
Empirically, moving from a grid spacing of 0.04 to a continuous location yields a ~3–6% increase in total radius sum for 26 circles. Combined with the global combinatorial search that already pushes the sum close to the theoretical upper bound (~2.67 for 26 circles), we anticipate a final sum **≥ 2.66**, comfortably beating the target 2.636.

### Implementation Skeleton (no code)

1. **Import** `numpy`, `scipy.optimize`, and a MILP interface (`ortools.linear_solver`).
2. **generate_candidates(g, radius_levels)** → list of `(x, y, r)`.
3. **build_milp(candidates)**:
   - Create binary variables `z_k`.
   - For each grid point, add “≤ 1” sum constraint.
   - Add total‑count constraint.
   - For each unordered pair, create continuous `dx_ij, dy_ij` and the four linear constraints described in 1.3.
   - Set objective `Σ r_k * z_k`.
   - Return solver object.
4. **solve_milp(solver)** → selected indices.
5. **extract_initial_solution(selected_indices, candidates)** → arrays `centers0`, `radii0`.
6. **shrink_initial(radii0, δ)**.
7. **pack_variables(centers0, radii0)** → flattened vector `z0`.
8. **define_objective(z)**, **define_jacobian(z)**.
9. **define_constraints(z)** returning a list of dicts for `trust-constr` (each with `fun`, `jac`).
10. **call minimize** with method `'trust-constr'`, bounds `[0,1]` for `x,y` and `[0,0.5]` for `r`.
11. **unpack solution**, **repair**, **compute sum_r**.
12. **validate** using the provided `validate_packing`. If it fails, raise an exception (so the caller sees the error).
13. **return** `(centers, radii, sum_r)`.

### Anticipated Failure Modes & Mitigations

| Failure | Reason | Mitigation |
|---------|--------|------------|
| MILP too large for CBC (memory/time) | Pairwise auxiliary vars explode with many candidates. | Reduce grid resolution (increase spacing) or prune candidates aggressively by discarding any with radius < 0.025. The NLP can later grow small circles if needed. |
| L∞ linearisation too conservative → overly small initial sum | The sufficient condition may cut off feasible configurations. | After MILP, run a *local expansion* pass: for each selected circle, compute the exact Euclidean distances to neighbours, enlarge the radius to the minimum of side distance and half of those Euclidean distances, then feed to NLP. This step bridges the gap between the conservative L∞ and true Euclidean model. |
| Trust‑constr stagnates at a local optimum far from global | Starting point may sit in a narrow basin. | Run a second refinement with a small random perturbation of centres (e.g., Gaussian noise σ=0.005) and keep the best feasible result. Because the problem is low‑dimensional, only a few restarts are needed. |
| Numerical violation of constraints >1e‑12 leading to validator failure | Solver tolerances may be looser than validator’s strict 1e‑12. | After final solution, apply the deterministic repair loop with a safety subtraction `ε = 1e‑9` from each radius before validation. This guarantees a margin. |
| Edge case where a circle touches a wall exactly (x‑r = 0) and validator flags due to -1e‑12 tolerance. | Exact equality may be judged as outside because of floating‑point rounding. | After repair, set `r_i = min(r_i, x_i, 1-x_i, y_i, 1-y_i) - 1e‑10` to push it strictly inside. |
