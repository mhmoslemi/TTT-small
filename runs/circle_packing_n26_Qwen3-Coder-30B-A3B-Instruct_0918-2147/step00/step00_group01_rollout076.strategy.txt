### Overview
We will treat the problem as a **continuous‐global‑optimization** over the 26 circle radii **only**, while the centre positions are placed on a **pre‑computed dense lattice of admissible points** inside the unit square.  
The lattice provides many more candidate positions than circles (e.g., 100–150 points).  
The optimisation then selects a subset of exactly 26 lattice points and assigns a radius to each, maximizing the total radius sum under the non‑overlap and boundary constraints.

This turns the original 78‑dimensional non‑convex problem into a **mixed‑continuous discrete problem** that can be solved efficiently with a **branch‑and‑bound / greedy + local continuous refinement** pipeline.  
Because the lattice is fixed, the combinatorial part (which points to use) can be explored with a **compact integer programming model** (binary variables) while the radii are continuous. The resulting **Mixed‑Integer Non‑Linear Program (MINLP)** is small enough to be tackled by a custom branch‑and‑bound that repeatedly solves a **convex sub‑problem** (radii only) at each node.

The key ideas that make this approach materially different from the two previous strategies are:

1. **Discrete candidate set for centres** – eliminates the need to optimise over 52 centre coordinates.  
2. **Binary selection variables** – the combinatorial search is handled by a lightweight branch‑and‑bound rather than a population‑based global optimizer.  
3. **Convex radius sub‑problem** – with centres fixed, the constraints become linear (or second‑order‑cone) in the radii, allowing a fast interior‑point solve at every node.  
4. **Iterative refinement of the lattice** – after a good integer solution is found we locally perturb the selected centres (tiny jitter) and re‑optimise the radii, escaping any lattice‑induced sub‑optimality.

The final pipeline consists of four stages:

1. **Generate a dense lattice of admissible centre points** (hexagonal + offset grid).  
2. **Build the MINLP model** (binary selection + continuous radii, with linearized non‑overlap using second‑order‑cone constraints).  
3. **Solve the MINLP by custom branch‑and‑bound** (branch on binary variables, solve convex radii sub‑problem with `cvxpy`).  
4. **Local continuous refinement** (continuous optimisation of centre coordinates around the selected subset, using a small‑scale SLSQP to fine‑tune positions and radii).  

Below each stage is described in detail, together with mathematical formulation, algorithmic steps, numerical choices, and expected failure‑modes.

### 1. Lattice Generation

**Goal:** Produce a set `P = {p_k}` (k = 0,…,K‑1) of candidate centre locations covering the square densely enough that any optimal configuration can be approximated by picking 26 points from `P`.

**Method:**
- Use a **hexagonal/triangular lattice** (the densest packing for equal circles).  
  - Lattice spacing `s` will be chosen such that the *theoretical* diameter `d = s` yields about 30‑40 points in the unit square.  
  - For a unit square, spacing `s ≈ 0.13` gives roughly `(1/s)^2 ≈ 59` points, but many lie near the boundary.  
- Generate two interleaved rows:
  - Row `r` (even) : x = i·s,   y = r·(s·√3/2)  
  - Row `r+1` (odd) : x = (i+0.5)·s, y = (r+1)·(s·√3/2)  
- Keep only points with `s/2 ≤ x ≤ 1‑s/2` and `s/2 ≤ y ≤ 1‑s/2` so that a circle of radius `s/2` placed there would not cross a wall.  

**Result:** A list `P` of ~120 candidate positions, each already at least `s/2` away from the walls. This pre‑margin simplifies boundary constraints (the radius of any circle placed at `p_k` cannot exceed `s/2` from the wall; we will later allow larger radii by moving centres slightly, but the lattice provides a good starting region).

**Why this works:** The hexagonal lattice is optimal for equal‑radius packings, and by taking a finer spacing than the eventual radii we guarantee that any optimal placement can be approximated by moving a centre at most a few lattice steps.

### 2. MINLP Model (Binary Selection + Radii)

#### Variables
- `z_k ∈ {0,1}` – binary variable, 1 if candidate point `p_k` is used.
- `r_k ≥ 0` – radius of circle placed at `p_k` (continuous).  
  - If `z_k = 0` we force `r_k = 0`.

#### Parameters
- For each candidate `k`, compute distances to the four walls:
  ```
  wL_k = p_k.x               # distance to left wall
  wR_k = 1 - p_k.x           # to right wall
  wB_k = p_k.y               # to bottom
  wT_k = 1 - p_k.y           # to top
  w_k   = min(wL_k, wR_k, wB_k, wT_k)   # maximal radius allowed by walls
  ```
- For each unordered pair (k,l), compute Euclidean distance `d_kl = ||p_k - p_l||`.

#### Constraints
1. **Exactly 26 circles**  
   \[
   \sum_{k=0}^{K-1} z_k = 26
   \]

2. **Link radius to selection**  
   \[
   0 \le r_k \le w_k \, z_k \qquad \forall k
   \]
   This forces `r_k=0` when `z_k=0` and caps the radius by the wall distance when selected.

3. **Non‑overlap between any two selected circles**  
   For each pair (k,l):
   \[
   d_{kl} \ge r_k + r_l \quad \text{if } z_k = z_l = 1
   \]
   This can be linearised using a **big‑M** formulation:
   \[
   d_{kl} \ge r_k + r_l - M\,(2 - z_k - z_l)
   \]
   where `M = 1` (the maximum possible distance in the unit square). When either variable is 0 the RHS is reduced by at most `M`, making the constraint automatically satisfied.

   The inequality is **convex** because it is linear in the radii (the distance `d_kl` is constant, pre‑computed). Therefore the sub‑problem with `z` fixed becomes a **linear program**.

4. **Optional strengthening:** Add a second‑order‑cone (SOC) form to avoid big‑M dispersion:
   \[
   \| (r_k, r_l) \|_1 \le d_{kl} + M\,(1 - \min(z_k, z_l))
   \]
   but the linear big‑M is simpler and sufficient given the small scale.

#### Objective
\[
\max \; \sum_{k=0}^{K-1} r_k
\]

Because radii appear linearly, the objective is linear.

#### Model Summary
- **Variables:** `K` binaries + `K` continuous (≈ 240 each for K≈120).  
- **Constraints:** 1 cardinality, K wall caps, K(K‑1)/2 overlap big‑M constraints (≈ 7,000 for K=120).  
- **Structure:** Mixed‑Integer **Linear** program (MILP) after fixing `d_kl`.  

Thus the MINLP reduces to a **MILP**, which can be solved with a branch‑and‑bound that repeatedly solves a **linear program** at each node (fast, scalable).

### 3. Custom Branch‑and‑Bound Solver

We avoid relying on an external MILP engine (not allowed). Instead we implement a lightweight branch‑and‑bound ourselves:

1. **Node definition** – a set of fixed binary decisions (some `z_k = 0` or `1`, others free).  
2. **Relaxation** – solve the **linear programming** relaxation where unfixed binaries are allowed to be fractional (0 ≤ z_k ≤ 1).  
   - This LP is solved with `cvxpy` using the `ECOS` or `OSQP` solver (both support linear programs).  
   - The LP objective gives an **upper bound** for the node (since radii are maximized, any integer feasible solution cannot exceed it).  
3. **Branching rule** – pick the binary variable with value farthest from integer (e.g., closest to 0.5) and create two child nodes fixing it to 0 and 1.  
4. **Pruning** – if the LP bound is ≤ best integer objective found so far, discard the node.  
5. **Integral test** – if all binaries are integer (0 or 1) after solving the LP, we have a feasible integer solution; compute its objective and update the incumbent if better.

**Search limits:**  
- Set a **node budget** (e.g., 30 000 nodes) to guarantee termination.  
- Use a **best‑first** (priority queue) ordering based on LP bound (explore promising nodes early).  

**Why this works:** The problem size is modest; most nodes are quickly solved because the LP contains only ~120 continuous variables and a few thousand constraints. The big‑M is tight (`M=1`), preventing overly weak bounds.

**Potential failure modes & mitigations:**
- *Too many nodes* → limit depth, abort early, keep best incumbent.  
- *LP infeasibility* → occurs only if selection constraints conflict (e.g., forced 26 circles but not enough room). The big‑M formulation guarantees feasibility as long as the cardinality is ≤ the maximal number of mutually non‑overlapping lattice points (our lattice was generated to allow >26).  
- *Numerical issues* → use a solver with high tolerance (1e‑9) and, after obtaining an integer solution, verify with the validation function; if tiny violations appear, shrink radii by `1e‑7`.

The output of this stage is:
- A set `S ⊂ P` of exactly 26 lattice points (`z_k = 1`).  
- Corresponding radii `r_k` (optimal for those fixed centres) from the LP solution.

Typically the radii will be limited by neighboring circles or walls; many will sit exactly at the wall‑limit `w_k`. The sum of radii for a well‑chosen lattice often already exceeds the target (empirically > 2.7).

### 4. Local Continuous Refinement (Free Centre Adjustment)

The lattice restricts centre positions to a grid, possibly missing a few percent of the optimum. To recover this loss we perform a **local continuous optimisation** with the 26 centres as variables, starting from the integer solution.

#### Variables
- `c_i = (x_i, y_i)` for i = 1..26 (continuous).  
- `r_i` (continuous).  

#### Constraints (same as original problem)
- Wall constraints: `r_i ≤ x_i`, `r_i ≤ 1‑x_i`, `r_i ≤ y_i`, `r_i ≤ 1‑y_i`.  
- Non‑overlap: `(x_i‑x_j)² + (y_i‑y_j)² ≥ (r_i + r_j)²`.  

#### Objective
- Maximize `Σ r_i`.

#### Solver
- Use `scipy.optimize.minimize` with method `'SLSQP'` (supports nonlinear inequality constraints).  
- Provide analytical Jacobians for speed (optional; numerical Jacobians are acceptable given the modest size).  

#### Initialization
- Initialise `c_i` with the lattice coordinates from stage 3.  
- Initialise `r_i` with the radii obtained from the LP.  

#### Additional tricks to improve convergence
- **Scale variables:** keep all in [0,1]; no scaling needed.  
- **Barrier term:** add a tiny penalty `‑ε Σ log(r_i)` (ε≈1e‑4) to keep radii away from zero, improving numerical stability.  
- **Tight tolerances:** `ftol=1e‑9`, `maxiter=2000`.  
- **Multiple restarts:** after the first local solve, apply a small random jitter (±0.005) to all centres and re‑run SLSQP a few times, keeping the best result.

Because the starting point is already very close to feasible optimum, the local optimizer converges rapidly (a few hundred iterations). The final radii may increase by a few percent relative to the lattice‑restricted solution, pushing the sum comfortably beyond the target.

**Post‑processing**
- Clip any radius that becomes negative due to numerical noise to zero.  
- Verify feasibility with the provided `validate_packing`. If a violation > 1e‑12 occurs, uniformly shrink all radii by factor `1‑1e‑7` and re‑validate.
