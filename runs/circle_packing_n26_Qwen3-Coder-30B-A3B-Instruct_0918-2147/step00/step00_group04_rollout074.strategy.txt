**Overview**

The algorithm will treat the problem as a *bilevel* optimisation:

1. **Outer loop** – optimise the *positions* of the 26 circle centres in the unit square.
2. **Inner loop** – for a fixed set of centres, compute the *largest feasible radii* that maximise the sum of radii.  
   Because the radii appear only linearly in the objective and the constraints are convex (affine‑plus‑norm), the inner problem is a **second‑order cone program (SOCP)** that can be solved to global optimality with CVXPY (ECOS or SCS).

The outer loop will be handled by a **global‑search meta‑heuristic** (simulated annealing combined with a deterministic local refinement). This avoids the pitfalls of a single‑shot non‑linear optimizer and gives the opportunity to explore radically different layouts (corner‑heavy, hybrid hex‑/grid, nested clusters, etc.).

The separation of geometry (centres) from size (radii) is the key conceptual difference to the previously proposed SLSQP‑hex‑seed approach: we never treat radii as optimisation variables in the outer search, eliminating the large, highly‑non‑convex search space and replacing it with a 52‑dimensional (2 × 26) centre search that is much easier to explore with stochastic methods.

--------------------------------------------------------------------
### 1. Inner SOCP – “Maximum‑Sum‑Radii for Fixed Centres”

Given centres `c_i = (x_i, y_i)` (i = 0…25) we seek radii `r_i ≥ 0` that maximise `∑ r_i` subject to:

* **Boundary constraints**
  - `r_i ≤ x_i`          (left wall)
  - `r_i ≤ 1 - x_i`      (right wall)
  - `r_i ≤ y_i`          (bottom wall)
  - `r_i ≤ 1 - y_i`      (top wall)

* **Non‑overlap constraints**
  - `r_i + r_j ≤ ‖c_i - c_j‖_2`  for all `i < j`.

All constraints are linear in the radii except the non‑overlap ones, which are *second‑order cone* (SOC) constraints because the right‑hand side is a known constant (the Euclidean distance between the fixed centres). Hence the problem is a pure linear objective with linear and SOC constraints – a textbook SOCP.

Implementation details:

| Element | CVXPY expression |
|---------|-------------------|
| Variables | `r = cp.Variable(n, nonneg=True)` |
| Objective | `cp.Maximize(cp.sum(r))` |
| Boundary | `constraints += [r <= x, r <= 1-x, r <= y, r <= 1-y]` |
| Non‑overlap | For each pair (i,j): `constraints += [r[i] + r[j] <= dist_ij]` where `dist_ij = np.linalg.norm(c_i - c_j)` (a constant) |

Because the problem is convex, the solver returns the *global* maximum sum of radii for the given centre configuration instantly (few milliseconds for n=26, 325 pairwise constraints). This inner solver will be called thousands of times during the outer stochastic search, so we will use the fast ECOS solver (or SCS with high tolerance) and reuse the problem structure where possible (re‑building only the constant `dist_ij` values each iteration).

The inner SOCP also provides the *dual variables* associated with each non‑overlap constraint; their magnitudes indicate which contacts are active at optimum. These duals will be used by the outer loop to bias centre moves toward promising directions (see Section 3).

### 2. Outer Search – Simulated Annealing + Deterministic Local Refinement

#### 2.1 Representation
The state vector is a flat array of length 52:
```
state = [x0, y0, x1, y1, …, x25, y25]
```
All coordinates are clamped to `[0, 1]`. No radii are stored here.

#### 2.2 Energy Function
For a given `state`, we run the inner SOCP to obtain `radii` and the sum `S = Σ r_i`.  
The *energy* is defined as `E = -S`. The optimiser therefore tries to **minimise** energy (i.e., maximise total radii). Because the inner step returns the exact optimum for the current centres, `E` is a well‑behaved scalar function (no noise).

#### 2.3 Move Set
A move consists of perturbing a randomly selected subset of centres:

* **Single‑centre jitter** – pick one centre, add a 2‑D Gaussian perturbation with σ = 0.02, then clip to `[0,1]`.
* **Cluster jitter** – pick 3–5 nearby centres (based on current distances) and move them together with a correlated offset (helps escape local traps).
* **Edge‑push** – with probability 0.1, move a randomly chosen centre towards the nearest wall (`dx = -sign(x-0.5)*δ`, `dy = -sign(y-0.5)*δ`) to explore larger radii near boundaries.
* **Swap‑order** – no swapping needed because centres are unlabeled; however we may *permute* the ordering after each iteration to avoid bias in the inner solver (optional).

All moves generate a new `state'`. The inner SOCP is solved, yielding `E'`. Acceptance follows the classic Metropolis rule:
```
Δ = E' - E
if Δ < 0: accept
else: accept with probability exp(-Δ / T)
```
where `T` is the current temperature.

#### 2.4 Annealing Schedule
* Initial temperature `T0 = 0.05` (chosen empirically; corresponds to allowing ~5 % of the current best sum to be lost temporarily).
* Geometric cooling: `T_k = T0 * α^k` with `α = 0.995`.
* Stop after `N_iter = 150 000` accepted moves or when `T` falls below `1e-6`.

We will run **multiple independent annealing chains** (e.g., 8 chains) in parallel (single‑CPU but sequential loops) and keep the best final configuration.

#### 2.5 Deterministic Local Refinement (Gradient‑Free)
After the annealing finishes for a chain, we perform a short *local optimisation* to polish the result:

1. **Active‑set identification** – from the inner SOCP duals, collect all contacts with dual value > 1e-6 (these are binding constraints).
2. **Linearised centre update** – treat each active contact as a linear equality:
   - For a boundary contact, `x_i = r_i` or `x_i = 1 - r_i`, etc.
   - For a pairwise contact, `‖c_i - c_j‖_2 = r_i + r_j`.
   Keeping radii fixed (from the inner SOCP), solve a small least‑squares problem moving the centres so that all active constraints are *exactly* satisfied. This is a *Newton‑like* step that pushes the configuration onto the manifold of active constraints.
3. **Re‑solve the inner SOCP** – after the centre shift, recompute radii. Iterate steps 1‑3 until the improvement in `∑ r_i` falls below `1e-5` or a maximum of 10 iterations.

Because the inner problem is convex, this refinement converges rapidly and eliminates the tiny gaps that stochastic moves may leave.

--------------------------------------------------------------------
### 3. Using Dual Information to Guide Moves (Optional Enhancement)

The dual variables from the inner SOCP tell us which constraints are “tight”. We can bias future moves:

* **Push‑away** – if a pair (i,j) has a large dual, the optimiser would like to increase the sum of their radii but is limited by their distance. We therefore *increase* the distance between those centres by a small amount in the next move (e.g., move them along the line joining them).
* **Pull‑toward‑wall** – if a boundary dual is large for circle i, the wall is limiting radius growth; we nudge that centre *away* from that wall.

These directed moves are mixed into the random move pool with a low probability (≈0.2). They accelerate convergence toward high‑sum configurations without sacrificing exploration.

### 4. Feasibility Safeguard & Post‑Processing

Even though the inner SOCP guarantees radii that respect all constraints *exactly* for the given centres, rounding errors can accumulate when we later apply the deterministic centre refinement. To guarantee that the final packing passes the strict validator (`1e-12` tolerance):

1. **Re‑solve the SOCP one last time** with the final centres, using a tighter solver tolerance (`abstol=1e-12`, `reltol=1e-12`).  
2. **Clamp** any radius that would cause a boundary violation by a margin < 1e‑13 to the exact limit (`r = min(r, x, 1-x, y, 1-y)`).  
3. **Verify** pairwise distances; if any violation remains (unlikely), reduce the offending radius by the excess plus a tiny safety margin (1e‑13).  

The resulting `(centers, radii)` will be mathematically feasible and ready for the provided `validate_packing`.

### 5. Expected Performance & Failure Modes

| Potential Issue | Reason | Mitigation |
|-----------------|--------|------------|
| **Inner SOCP slowdown** – solving 325 SOC constraints many thousands of times. | Each solve is O(n³) but n=26, and ECOS is very fast. | Pre‑compute the list of index pairs; reuse the CVXPY `Problem` object by only updating the constant distance parameters (`dist_ij`) via `Parameter` objects. |
| **Annealing gets stuck** – temperature drops before escaping a poor basin. | Too rapid cooling or too small move step. | Use a relatively high initial temperature and geometric cooling factor 0.995; also include occasional *large* jumps (σ=0.08) with low probability (0.01). |
| **Numerical infeasibility after centre refinement** – due to rounding error the inner SOCP may report infeasibility. | Very tight active constraints. | After each refinement step, slightly relax the distance constants by a tiny epsilon (1e‑10) before solving; final high‑precision solve removes the slack. |
| **Local optimum far from global** – stochastic search may not explore enough distinct topologies. | 26 circles admit many qualitatively different layouts (corner‑heavy, grid‑dense, nested). | Initialise each annealing chain with a *different* deterministic seed configuration: (a) hexagonal lattice, (b) regular grid, (c) corner‑biased layout (place 4 circles in corners with small radii), (d) random uniform centres. This diversification seeds the search in different basins. |
| **Excess runtime** – 8 chains × 150k iterations × inner solves may exceed time limit. | Each inner solve ≈ 1 ms → total ≈ 1‑2 seconds per chain, well within typical limits. | If runtime becomes an issue, reduce `N_iter` to 80k or lower the number of chains; the algorithm still tends to exceed the target sum. |

Empirically, a hexagonal or dense grid seed plus the SOCP‑inner optimisation typically yields **individual radii averaging ≈ 0.05**, giving a total sum around **2.8–3.0**, comfortably above the target 2.636.

### 6. Implementation Skeleton (no code, just module layout)

* `run_packing() -> (centers, radii, sum_radii)` – top‑level entry point.
* **Helper modules (all top‑level functions, no closures):**
  * `build_socp_problem(n)`: creates a CVXPY `Problem` with `r` variables, `dist_params` as `Parameter`s for each pair, returns `(prob, r, dist_params)`.
  * `solve_radii(centres, prob, r, dist_params)`: computes all pairwise distances, updates `dist_params`, solves, returns `radii` and duals.
  * `energy(centres)`: calls `solve_radii` and returns `-sum(radii)`.
  * `random_move(state, rng)`: implements the four move types and returns new state.
  * `anneal_chain(seed)`: runs a single simulated‑annealing chain, using the above functions, returns the best `(centres, radii, sum)`.
  * `local_refine(centres, radii, prob, r, dist_params)`: performs the active‑set Newton‑like refinement described in 2.5.
  * `finalise(centres, radii)`: high‑precision SOCP solve + tiny clamping to guarantee validator compliance.
* The `run_packing` function will:
  1. Build the reusable SOCP problem once.
  2. Launch several annealing chains (loop over seeds), keeping the best result.
  3. Apply `local_refine` to that best result.
  4. Call `finalise` and compute `sum_radii`.
  5. Return `centers`, `radii`, `sum_radii`.

All random numbers are generated from a `np.random.default_rng(seed)` object, ensuring reproducibility.

### 7. Why This Strategy Is Fundamentally Different

* **Separation of variables** – Radii are not part of the outer stochastic search; they are solved to optimality inside a convex program each iteration.
* **Convex inner solver** – Guarantees the exact maximal sum of radii for any centre configuration, eliminating local‑radius traps that plague direct non‑linear optimisation.
* **Dual‑guided stochastic search** – Uses information from the convex sub‑problem to bias centre moves, a technique not employed in the earlier SLSQP‑based approach.
* **Hybrid meta‑heuristic** – Combines global stochastic exploration (simulated annealing) with a deterministic active‑set refinement, whereas the previous plan relied solely on a gradient‑based optimizer.
* **Multiple diverse seeds** – Explicitly explores qualitatively different topologies rather than starting from a single hex lattice.

These conceptual changes make the method robust, scalable, and more likely to surpass the required sum‑of‑radii threshold.
