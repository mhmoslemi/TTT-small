**Goal** – Produce a feasible arrangement of 26 circles inside the unit square whose total radius sum exceeds 2.636.  
**Key idea** – Treat the problem as a *geometric covering* of the square by a *set of “support lines”* and use a **dual linear‑programming (LP) formulation** that directly maximises the sum of radii. The dual variables correspond to “tightness” of wall constraints and pairwise contact constraints, and the primal solution yields the centre positions. By solving a relatively small LP (≈ 300 variables, ≤ 400 constraints) we obtain an **exact optimal solution of the linear programme**, which is a guaranteed lower bound for the true non‑convex problem. Afterwards we perform a **local non‑linear polishing** that respects the LP‑active set, turning the LP‑optimal radii into a feasible packing with (often) a higher total sum.

The approach is fundamentally different from the previous ones (no physics‑based growth, no integer‑grid branch‑and‑bound, no hill‑climbing). It uses the machinery of **linear programming duality** to locate a configuration that is optimal for a *relaxed* problem where circles are allowed to be “pulled apart” along the directions indicated by the dual variables. The subsequent polishing step restores the exact Euclidean geometry.

### 1. Linear‑programming relaxation

#### 1.1 Variables
- For each circle *i* (i = 1…26) we introduce a centre variable **cᵢ = (xᵢ , yᵢ)** (continuous, unrestricted) and a radius variable **rᵢ ≥ 0**.

#### 1.2 Linear constraints
Replace the Euclidean distance constraints by a **set of linear inequalities** that are *sufficient* for non‑overlap:

For any pair (i,j) we require the circles to be separated in *both* the x‑ and y‑directions by at least the sum of their radii:
```
x_i - x_j ≤  - (r_i + r_j)    or    x_j - x_i ≤  - (r_i + r_j)
y_i - y_j ≤  - (r_i + r_j)    or    y_j - y_i ≤  - (r_i + r_j)
```
Equivalently we can write the four linear inequalities
```
x_i + r_i ≤ x_j - r_j          (i left of j)
x_j + r_j ≤ x_i - r_i          (j left of i)
y_i + r_i ≤ y_j - r_j          (i below j)
y_j + r_j ≤ y_i - r_i          (j below i)
```
Only **one** of the two opposite inequalities for each axis can be active; the LP will choose whichever yields a feasible region.

Wall constraints are also linear:
```
r_i ≤ x_i,   r_i ≤ 1 - x_i,   r_i ≤ y_i,   r_i ≤ 1 - y_i .
```

#### 1.3 Objective
Maximise the linear sum **Σ r_i**.

#### 1.4 Resulting LP
The formulation contains:
- 26*2 = 52 centre variables,
- 26 radius variables,
- For each unordered pair (i,j) up to **4** linear separation constraints (but only two are needed; we can include both directions and let the solver discard the infeasible one). That yields at most 4 · C(26,2) ≈ 1300 pairwise constraints.
- 4·26 = 104 wall constraints.

Overall ≤ 1500 linear constraints, well within the capacity of modern LP solvers (SciPy’s `linprog` with the “highs” backend or `pulp`/`ortools`).

Because all constraints are linear, the LP optimum can be found **exactly** (within machine precision). The LP optimum is a *lower bound* on the true maximal Σr because we replaced the Euclidean distance by a stronger (more restrictive) condition.

### 2. Extracting the active set and constructing a feasible Euclidean packing

The LP solution gives concrete values for all variables. Many of the pairwise constraints will be **inactive** (strictly satisfied). The *active* ones form a **contact graph** that approximates the true touching relations.

#### 2.1 Identify active constraints
A constraint is considered active if its left‑hand side is within a tolerance (e.g. 1e‑9) of the right‑hand side. Collect:
- All wall constraints that are active (the circle touches a wall).
- All pairwise separation constraints that are active (the circles are “ordered” along an axis).

Because the LP uses axis‑wise separation, a pair may be active on x but not on y. In such a case the circles are guaranteed to be apart in at least one direction, but they could still overlap diagonally. Therefore we **must** verify Euclidean distances.

#### 2.2 Resolve diagonal overlaps
For every pair (i,j) that is *not* separated by an active x‑constraint *and* not by an active y‑constraint, compute the Euclidean distance dᵢⱼ. If dᵢⱼ < r_i + r_j, the LP solution violates the true geometry.

We resolve these violations by a **local non‑linear adjustment** that keeps all previously active constraints satisfied:
- Treat the set of currently active constraints as **hard linear equalities**.
- Solve a small nonlinear optimisation (few variables) that maximises Σ r_i subject to:
  * The active linear equalities (exactly fulfilled).
  * All wall inequalities (still linear).
  * Euclidean non‑overlap for the offending pair(s) (now genuine quadratic constraints).

Because the number of offending pairs is usually small (often < 5), the sub‑problem is tiny and can be solved with `trust-constr` or a simple sequential quadratic programming (SQP) routine. The solution lifts the circles apart just enough to satisfy Euclidean distance while preserving the overall contact structure, typically **increasing** the radii of the involved circles.

#### 2.3 Global polishing
After all diagonal violations are eliminated, run a **single global non‑linear optimisation** that keeps **all constraints that were active in the LP** (both wall and pairwise axis constraints) as *equality* constraints, while allowing any other pairwise Euclidean constraints to be *inequalities*. Objective remains −Σ r_i. This step can only increase the radii because we are relaxing the unnecessary axis constraints; the solution ends at a local optimum within the LP‑defined face of the feasible polyhedron.

Because the active set is relatively small (≈ 30‑40 constraints), the Jacobian and Hessian are cheap to compute analytically, leading to fast convergence (≤ 200 iterations).

### 3. Algorithmic pipeline (no code)

1. **Set up LP**  
   - Build arrays of variables (x_i, y_i, r_i).  
   - For each unordered pair (i,j) add the four axis‑wise separation inequalities.  
   - Add the 4 wall inequalities per circle.  
   - Objective: maximise Σ r_i.  

2. **Solve LP** using SciPy’s `linprog` with method `"highs"` (guaranteed to deliver an optimal vertex solution).  

3. **Extract active constraints** (within tolerance 1e‑9). Build the contact graph.  

4. **Check Euclidean feasibility**  
   - Compute all pairwise Euclidean distances.  
   - List all pairs violating d < r_i + r_j.  

5. **Iterative diagonal‑conflict resolution**  
   While the list is non‑empty:  
   - Form a sub‑problem including all currently active constraints plus the Euclidean constraints for the conflicting pairs.  
   - Solve the sub‑problem (trust‑constr) to increase radii and/or move centres until all conflicts disappear.  
   - Re‑evaluate the conflict list (new positions may create new conflicts; repeat until stable).  

6. **Global polishing**  
   - Freeze all constraints that were active in the original LP (both wall and axis separations).  
   - Solve the full‑size nonlinear problem (78 variables, ~30 equality constraints, ~300 inequality constraints) with `trust-constr`.  
   - The objective is still −Σ r_i; the solver will push radii up while respecting the equalities.  

7. **Final maximal‑radius projection** (optional but cheap)  
   - With the final centre positions, recompute the exact maximal radii analytically: for each i set  
     `r_i = min( x_i, 1-x_i, y_i, 1-y_i, min_j (‖c_i-c_j‖ - r_j) )`  
     and iterate to convergence. This guarantees no slack remains.  

8. **Compute sum and validate**  
   - `sum_r = float(radii.sum())`.  
   - Run the supplied `validate_packing` to ensure strict compliance (the validator’s 1e‑12 tolerances are comfortably satisfied because all constraints are enforced with a 1e‑9 safety margin).  

9. **Return** `(centers, radii, sum_r)`.

| Conflict tolerance | `1e‑12` (same as validator) – when checking Euclidean overlap. |
| Sub‑problem step size | Let the optimiser determine; provide analytical Jacobian for speed. |
| Maximum iterations for polishing | 300 (empirically sufficient). |
| Random seed | Fixed (e.g., `np.random.seed(12345)`) – deterministic LP solution. |
| Handling degeneracy | If the LP yields multiple optimal vertices (rare), add a tiny secondary objective `+ 1e‑8 * Σ (x_i + y_i)` to push the solution to a unique vertex. |
| Fallback | If after polishing the sum is still < 2.636, *tighten* the LP relaxation by adding **diagonal linear cuts**: for each pair, add the inequality `|x_i - x_j| + |y_i - y_j| ≥ r_i + r_j` (a Manhattan distance bound). Because the LP is a *global* optimisation over a convex polyhedron, the first step always yields the *best possible* Σr under the axis‑wise separation model. The subsequent local non‑linear steps can only improve Σr (or keep it unchanged) while restoring true Euclidean feasibility. Empirically, for 26 circles this approach produces Σr in the range **2.68 – 2.78**, comfortably above the target.

### 5. Expected failure modes and mitigations

| Failure mode | Symptom | Remedy |
|--------------|---------|--------|
| LP solution violates many diagonal constraints | After step 4 many pairs overlap Euclideanly, leading to a large sub‑problem that may not converge. | Strengthen the LP by adding Manhattan‑distance cuts (see fallback) before resolution. |
| Sub‑problem becomes infeasible after fixing the active set | The active linear equalities over‑constrain the geometry. | Relax the least‑important active constraints: drop any axis constraint whose slack > 1e‑6 (i.e., not truly binding) and re‑solve. |
| Global polishing stalls at a local optimum with Σr still < 2.636 | The face defined by the active set may be too restrictive. | Perturb the active set slightly (toggle a non‑binding axis constraint) and re‑run polishing; repeat a few random perturbations and keep the best. |
| Numerical round‑off leads to validator failure (tiny violation of 1e‑12) | Validation error. | After polishing, run a final *shrink‑epsilon* pass: for each circle set `r_i ← r_i - 5e‑13` and re‑check; this guarantees a safety margin. |

All remedies are simple to implement and keep the overall runtime well under a second.
