```python
import torch
from torch import nn, einsum
import math

# Reference code in PyTorch
class TriMul(nn.Module):
    def __init__(
        self,
        dim: int,
        hidden_dim: int,
    ):
        super().__init__()

        self.norm = nn.LayerNorm(dim)

        self.left_proj = nn.Linear(dim, hidden_dim, bias=False)
        self.right_proj = nn.Linear(dim, hidden_dim, bias=False)

        self.left_gate = nn.Linear(dim, hidden_dim, bias=False)
        self.right_gate = nn.Linear(dim, hidden_dim, bias=False)
        self.out_gate = nn.Linear(dim, hidden_dim, bias=False)

        self.to_out_norm = nn.LayerNorm(hidden_dim)
        self.to_out = nn.Linear(hidden_dim, dim, bias=False)

    def forward(self, x: torch.Tensor, mask: torch.Tensor) -> torch.Tensor:
        """
        x: [bs, seq_len, seq_len, dim]
        mask: [bs, seq_len, seq_len]

        Returns:
            output: [bs, seq_len, seq_len, dim]
        """
        batch_size, seq_len, _, dim = x.shape

        x = self.norm(x)

        left = self.left_proj(x)
        right = self.right_proj(x)

        mask = mask.unsqueeze(-1)
        left = left * mask
        right = right * mask

        left_gate = self.left_gate(x).sigmoid()
        right_gate = self.right_gate(x).sigmoid()
        out_gate = self.out_gate(x).sigmoid()

        left = left * left_gate
        right = right * right_gate

        out = einsum('... i k d, ... j k d -> ... i j d', left, right)
        # This einsum is the same as the following:
        # out = torch.zeros(batch_size, seq_len, seq_len, dim, device=x.device)
        
        # # Compute using nested loops
        # for b in range(batch_size):
        #     for i in range(seq_len):
        #         for j in range(seq_len):
        #             # Compute each output element
        #             for k in range(seq_len):
        #                 out[b, i, j] += left[b, i, k, :] * right[b, j, k, :]

        out = self.to_out_norm(out)
        out = out * out_gate
        return self.to_out(out)
```

```python
@triton.jit
def matmul_persistent_ws_kernel(

   stride_am, stride_ak, stride_bk, stride_bn, stride_cm, stride_cn,

   offs_m_2 = pid_m * BLOCK_M + tl.arange(BLOCK_M // 2, BLOCK_M) # async_task 0, 1, 2
   offs_n = pid_n * BLOCK_SIZE_N + tl.arange(0, BLOCK_N) # async_task 0, 1, 2
   offs_k = tl.arange(0, BLOCK_K) # async_task 0

   b_ptrs = b_ptr + (offs_k[:, None] * stride_bk + offs_n[None, :] * stride_bn) # async_task 0

   acc_1 = tl.zeros((BLOCK_M // 2, BLOCK_N), dtype=tl.float32) # async_task 2
   for k in range(0, tl.cdiv(K, BLOCK_K)): # async_task 0, 1, 2
       a_1 = tl.load(a_ptrs_1)   # async_task 0
       a_2 = tl.load(a_ptrs_2)   # async_task 0
       b = tl.load(b_ptrs)   # async_task 0
       acc_1 += tl.dot(a_1, b)   # async_task 1
       acc_2 += tl.dot(a_2, b)   # async_task 2
       a_ptrs_1 += BLOCK_K * stride_ak # async_task 0
       a_ptrs_2 += BLOCK_K * stride_ak # async_task 0
       b_ptrs += BLOCK_K * stride_bk # async_task 0

   c_2 = acc_2.to(tl.float16) # async_task 2
   c_ptrs_1 = c_ptr_1 + stride_cm * offs_m_1[:, None] + stride_cn * offs_n[None, :] # async_task 1

   tl.store(c_ptrs_1, c_1) # async_task 1
   tl.store(c_ptrs_2, c_2) # async_task 2
```

## Triton launch convention

Every failure mode below has appeared in this search. Read this before writing.

A `@triton.jit` function is NOT a Python function. It is launched with a grid
subscript, and its `tl.constexpr` parameters exist only inside it:

```python
@triton.jit
def my_kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    m = offs < n
    tl.store(y_ptr + offs, tl.load(x_ptr + offs, mask=m, other=0.0), mask=m)

def custom_kernel(data):
    ...
    BLOCK = 128                                   # a host variable YOU define
    grid = (triton.cdiv(n, BLOCK),)               # host-side, use triton.cdiv
    my_kernel[grid](x, y, n, BLOCK=BLOCK)         # note the [grid] subscript
```

- `my_kernel(...)` without `[grid]` raises "Cannot call @triton.jit'd outside
  the scope of a kernel".
- `BLOCK`, `BLOCK_M`, `BLOCK_N` are not defined on the host unless you define
  them there. Referencing one you only declared as a `tl.constexpr` parameter
  raises NameError.
- `tl.cdiv` is device-side. On the host use `triton.cdiv`.
- Define the kernel at module top level, never nested inside `custom_kernel`.

You do not have to move everything into Triton. A correct submission that keeps
most of the computation in PyTorch and moves one hot region into a kernel scores;
one that fails to launch scores zero.

## Approach and rationale
### Problem Analysis
The TriMul operator performs a core operation in protein structure prediction models. It involves:
1. Normalizing input tensor with LayerNorm
2. Projecting through linear layers
3. Applying sigmoid gates
4. Mask multiplication
5. Outer-product reduction with einsum

The key bottleneck is the O(N³) operation (step 5) where N can be up to 1024. Standard `torch.einsum` handles this but does not utilize efficient GPU matrix multiplication through Tensor Cores.

### Triton Implementation Strategy
1. **Tiled Memory Layout**: We'll use a physically tiled layout where we dequeue all necessary elements in a single batch and scatter them into a shared buffer. Each thread will handle a block of tiles.
2. **Reduce Warp Level Flattening**: Instead of flattening outputs at warp level, we'll do it at thread block level to avoid atomic operations on non-tile-accesible memory.
3. **Input Handling**: The input is 4D [B, N, N, D] where:
   - B is batch size (1-2)
   - N is sequence length (256-1024)
   - D is channel dimension (128)
4. **Kernel Size Definition**: We'll define `BLOCK` and `GROUPS` as constexpr parameters matching NVIDIA Tensor Cores' expectations (D must be 128, N must be multiple of 8).

### Step-by-step Plan
We'll create a Triton kernel that:
1. Takes [B, N, N, D] input and corresponding mask
2. Dequeues all (i,k) and (j,k) pairs for projection
3. Combines u[k] vectors for each k using outer products
4. Regularizes with LayerNorm (applied globally)
5. Applies output gating with sigmoid
6. Projects back to output dimension

## Mathematical specification
Let `B = batch size, N = sequence length, D = channel dimension`.

The reduction is:
```
output[b,i,j,c] = Σ_{k=0}^{N-1} (left[b,i,k,:] · right[b,j,k,:] + feature_c)
```

But note: our approach physically separates dimensions to exploit coalesce history:

We can view this as a specialized case of matrix multiplication where:
- Left tensor `P` is B × N × D (dense)
- Right tensor `Q` is B × N × D (dense)

The final output is B × N × N × D where:
```
output[b,i,j,c] = Σ_{k=0}^{N-1} (P[b,i,k] · Q[b,j,k]) + output[b,i,j,c]
```

But this maintains full precision due to modeling constraints.

## Implementation procedure
### Step 1: Setup Data
Define a physically tiled input with:
- `BLOCK` threads along the sequence dimension
- `D` threads along the channel dimension

### Step 2: Queue Bytes
Within k ∈ [0, N-1]:
- Dequeue left tensor positions: (b,i,k,c)
- Dequeue right tensor positions: (b,j,k,c)
- Normalize and project locally

### Step 3: Outer Product
For each k:
- Rearrange data into GEMM-friendly formats (Tensor Core PT)
- Reduce over channel dimension

### Step 4: Handling
Regularization and gating are computationally lighter and safer.

### Step 5: Output Projection
Final reduction to original dimensions using `torch.nn.Linear` projection tensors.

## Approach and Rationale

The outgoing version of the Triangle Multiplicative Update (TriMul) operator requires efficient computation of a O(N^3) reduction, which is critical for performance in protein structure prediction models. We will implement a fully optimized Triton kernel solution for this reduction, allowing us to reach the target runtime of under 554 microseconds.

### Core Idea

We reframe the TriMul reduction from:
    output[b, i, j, d] = sum_{k=0}^{N-1} (left[b, i, k, d] * right[b, j, k, d] + gate[d])
to:
    output[b, i, j] = Matrix multiplication between reshaped left and right components

This allows us to leverage DenseBlock kernel capabilities and exploit the high-performance Tensor Cores on NVIDIA Ampere architecture GPUs like the B200.

### Key Steps

1. **Physical tiling**: Break the computation by the sequence dimension N
2. **Memory layout**: Arrange the reduction in a kernel-friendly layout
3. **Separate computations**: Isolate the reduction phase from others

### Dominant Bottleneck

The reduction step dominates the WGS. By optimizing it specifically using:

    - Small tile_size (64) for the reduction
    - Extracting the best reuse
    - Aligning with Tensor Core expectations

We can achieve significant speed-ups.

## Mathematical Specification

Let's define the inputs and outputs:

- Input: `x` shape [B, N, N, C] (withoutLayerNorm already applied)
- Output: `output` shape [B, N, N, C]

Our reduction operation:

    For each entry (i, j) in the output pyramid (the bloque)
        For each dimension c:
            temp = 0
            for each intermediate k in the sequence:
                temp += left[b, i, k, c] * right[b, j, k, c]
            output[b, i, j, c] += temp

But we need to transform this into a matrix multiplication format.
