For the pairwise CD, here's my implementation strategy:

The 1D optimization for pair (i, j):

```python
# a[k-i] for k = i, ..., i+n-1
d[i:i+n] += a
# -a[k-j] for k = j, ..., j+n-1
d[j:j+n] -= a
```

This is O(n) and very fast with NumPy.

For the 1D optimization, I'll use the following approach:
1. Compute `f(-a_j)`, `f(0)`, `f(a_i)`.
2. The minimum is in the interval that contains the decrease.
3. Use golden section search for ~40 iterations.

Each evaluation of f(t) requires computing `max(b + t*d)`, which is O(n) with NumPy.

Total cost per pair: O(n) for d, plus 40 * O(n) for the search = O(n).
For n pairs per sweep: O(n^2).

With n = 8192, each sweep is about 8192 * 8192 = 67M operations. In NumPy, this is vectorizable but 8192 pairs * 40 evaluations * 16383 elements = ~5.4 billion operations. That's too slow!

I need to reduce the number of evaluations per pair. Let me use a smarter 1D optimization:

**Method: Find the kink point directly.**
1. Find k_left = argmax(b + (-a_j) * d) = argmax(b - a_j * d).
2. Find k_right = argmax(b + a_i * d) = argmax(b + a_i * d).
3. If k_left == k_right, the minimum is at one of the endpoints (check both).
4. Otherwise, find the intersection of the two lines:
   - Line 1: `b[k_left] + t * d[k_left]`
   - Line 2: `b[k_right] + t * d[k_right]`
   - Intersection: `t* = (b[k_right] - b[k_left]) / (d[k_left] - d[k_right])` (if denominators differ)
5. Clamp t* to [-a_j, a_i].
6. Verify: evaluate f at t*, -a_j, a_i, and also at a few nearby points.
7. Take the best.

This is O(n) per pair (to compute the argmaxes and the intersection). No iterative search needed!

But we need to verify that t* is really the minimum. The issue is that the upper envelope might have more kinks between k_left and k_right. To handle this:
- After finding t*, evaluate f(t*) and also f at the endpoints.
- If f(t*) is not the minimum (shouldn't happen for convex f, but numerical issues), do a few iterations of ternary search.

In practice, the direct method should work well because the function is convex, and the intersection of the "extreme" lines gives the minimum (or very close to it).

```python
    """Find optimal transfer t between positions i and j."""
    n = len(a)
    # Compute d_k = a[k-i] - a[k-j]
    d = np.zeros(2 * n - 1, dtype=np.float64)
    d[i:i+n] += a
    d[j:j+n] -= a
    
    # Compute f at endpoints and candidate intersection
    a_i = a[i]
    a_j = a[j]
    t_lo = -a_j
    t_hi = a_i
    
    f_lo = np.max(b + t_lo * d)
    f_hi = np.max(b + t_hi * d)
    f_0 = np.max(b)  # t = 0
    
    # Find the argmax lines at each endpoint
    k_lo = np.argmax(b + t_lo * d)
    k_hi = np.argmax(b + t_hi * d)
    
    if k_lo == k_hi:
        # Same line dominates throughout
        best_t = t_lo if f_lo <= f_hi else t_hi
    else:
        # Find intersection
        dk_lo = d[k_lo]
        dk_hi = d[k_hi]
        if abs(dk_lo - dk_hi) < 1e-15:
            best_t = 0.0
        else:
            t_star = (b[k_hi] - b[k_lo]) / (dk_lo - dk_hi)
            t_star = max(t_lo, min(t_hi, t_star))
            
            # Verify
            f_star = np.max(b + t_star * d)
            best_t = t_star
            if f_lo < f_star:
                best_t = t_lo
            if f_hi < f_star:
                best_t = t_hi
    
    # Additional safety: check a few points around the candidate
    for t_check in [0.0, 0.5 * (t_lo + t_hi), best_t]:
        t_check = max(t_lo, min(t_hi, t_check))
        f_check = np.max(b + t_check * d)
        # We'll just track the best
    # Actually, let's just do 5 evaluations at evenly spaced points and the candidate
    # and take the min
    candidates = set([t_lo, t_hi, 0.0, best_t])
    if t_lo != t_hi:
        candidates.add(0.5 * (t_lo + t_hi))
    best_f = np.inf
    for t_c in candidates:
        t_c = max(t_lo, min(t_hi, float(t_c)))
        f_c = np.max(b + t_c * d)
        if f_c < best_f:
            best_f = f_c
            best_t = t_c
    
    return best_t
```

`delta_b_k = delta * (a[k-i] + a[k-i]) - delta * (a[k-j] + a[k-j])` (if all indices are distinct)
`= 2*delta * a[k-i] - 2*delta * a[k-j]`
`= 2*delta * (a[k-i] - a[k-j])`

But if `i = k-i` (i.e., `k = 2i`), then terms 1 and 2 are the same, and the change is `delta * 2*a[i] + delta^2` (from the quadratic term). Similarly for j.

For small delta, the linear approximation is good enough. And since we're doing exact line search (finding the optimal delta), the "a" in the formula should be the OLD value.

The issue is that when I compute `d_k = a[k-i] - a[k-j]`, I'm using the old `a`. The exact change (for the linear part) is `2 * delta * d_k`. So:
`b_k(new) ≈ b_k(old) + 2 * delta * d_k`

But this is only an approximation (ignoring the `delta^2` terms). For the 1D optimization, this means I'm solving a slightly different problem. In practice, since we're doing many small updates, this should be fine.

Actually, let me just use the approximation and recompute `b` from scratch periodically. The key insight is that the 1D optimization is still valid (approximately) with the linear model.

Let me revise the pairwise CD:

```python
    else:

        pairs = rng.permutation(n)
        n_pairs = n // 2
        improved = False
        
        for p in range(n_pairs):
            i = pairs[2 * p]
            j = pairs[2 * p + 1]
            
            a_i = a[i]
            a_j = a[j]
            
            if a_i < 1e-15 and a_j < 1e-15:
                continue

            d = np.zeros(2 * n - 1, dtype=np.float64)
            d[i:i+n] += a
            d[j:j+n] -= a

            t_hi = a_i

            # f(t) = max_k (b_k + 2*t*d_k)  [using 2*delta*d_k approximation]
            # But actually, the exact change is more subtle. Let's use the approximation:
            # b_k(new) ≈ b_k + 2*t*d_k  (for small t)
            # For larger t, this is an approximation. But the 1D optimization still
            # gives a good direction.
            
            # Evaluate at key points
            k_lo = np.argmax(b + 2 * t_lo * d)
            k_hi = np.argmax(b + 2 * t_hi * d)

                f_hi = np.max(b + 2 * t_hi * d)

                    best_t = t_lo
                elif f_hi <= min(f_lo, f_0):
                    best_t = t_hi
                else:
                    best_t = 0.0
            else:
                dk_lo = 2 * d[k_lo]
                dk_hi = 2 * d[k_hi]
                if abs(dk_lo - dk_hi) < 1e-15:
                    best_t = 0.0
                else:
                    t_star = (b[k_hi] - b[k_lo]) / (dk_lo - dk_hi)
                    best_t = max(t_lo, min(t_hi, t_star))
            
            # Verify
            f_best = np.inf
            for t_c in [best_t, 0.0]:
                t_c_clamped = max(t_lo, min(t_hi, float(t_c)))
                f_c = np.max(b + 2 * t_c_clamped * d)

                    f_best = f_c
                    best_t = t_c_clamped

                a[i] += best_t
                a[j] -= best_t

                b += 2 * best_t * d
                improved = True

                best_a = a.copy()
```

Wait, there's a problem. When I update `a[i]` and `a[j]`, the `d` vector for subsequent pairs is stale (it was computed with the old `a`). I need to either:
1. Recompute `d` for each pair (which I'm doing), or
2. Accept the staleness and recompute `b` periodically.

I'm recomputing `d` for each pair (using the current `a`), so that's fine. But the `b` update `b += 2 * best_t * d` is approximate (it only accounts for the linear change). After many pairs, `b` can accumulate error. So I recompute `b = fft_convolve_self(a)` at the end of each sweep.

This should be fine. The approximate `b` is only used for the 1D optimization within a sweep, and the exact `b` is used for tracking the best score.

Let me also think about the **FISTA with backtracking** more carefully. The issue with my previous implementation is that the backtracking requires evaluating the objective at trial points, which costs an FFT convolution each time. With 20 backtracking iterations, that's 20 FFTs per FISTA step, which is expensive.

A better approach: use the **smoothed objective** for the line search instead of the exact max. The smoothed objective `f_beta(a) = (1/beta) * log(sum exp(beta * b_k / S^2))` is smooth and cheap to evaluate (just a sum of exponentials, no additional FFT needed since we already have `b`).

Actually, we can be even smarter. During FISTA, we already compute `c = convolve(y, y)` at each step. We can use `c.max()` as the objective and the softmax-weighted gradient as the direction. The "line search" can be done by checking if the next iterate (after projection) has a lower `||c||_inf` than the current one.

But this requires computing the convolution at the trial point, which is one additional FFT. Let me just do that: one trial step per FISTA iteration.
