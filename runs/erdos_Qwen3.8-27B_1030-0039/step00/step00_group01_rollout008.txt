For a set of lines, the upper envelope can be found by computing the convex hull of the (slope, intercept) points. But for n=63 and 125 lines, we can just evaluate at all "interesting" points:
- x = 0
- x = 1
- x = (intercept_k - intercept_l) / (slope_l - slope_k) for all pairs where the two lines cross in [0,1]

But that's O(K²) pairs = O(n²) per coordinate, O(n³) per sweep. For n=63, that's 63³ * 125/63 = 63² * 125 ≈ 500K. Still fast.

Actually, there's a simpler approach. Since the upper envelope is convex and piecewise linear, its minimum over [0,1] is:
- If the slope of the envelope at 0 is ≥ 0 and at 1 is ≤ 0, the minimum is at the "valley" point
- Otherwise at a boundary

The slope of the envelope at x is determined by which line is active. We can binary search or just evaluate at all potential crossing points.

For simplicity and correctness, let me just evaluate at all crossing points plus boundaries:

```python
def optimize_coordinate(i, h, n, dx):
    """Find optimal value of h[i] given all other coordinates fixed"""
    # Compute slopes and intercepts for each lag
    K = 2 * n - 1
    slopes = np.zeros(K)
    intercepts = np.zeros(K)
    
    for s in range(-(n-1), n):
        k = s + n - 1
        # slope = ∂c[k]/∂h[i]
        slope = 0.0
        if 0 <= i - s < n:
            slope += (1.0 - h[i-s])
        if 0 <= i + s < n:
            slope -= h[i+s]
        slopes[k] = slope
        # intercept = c[k] - slope * h[i]
        # c[k] = slope * h[i] + intercept
        # We need c[k] at the current h
        # c[k] = sum over valid j of h[j]*(1-h[j-s])
        # = h[i]*(1-h[i-s]) * 1[valid] + h[i+s]*(1-h[i]) * 1[valid] + rest
        # Let's compute it directly (excluding i)
        c_val = 0.0
        for j in range(n):
            js = j - s
            if 0 <= js < n:
                if j == i:
                    c_val += 0  # h[i] contributes slope * h[i], excluded from intercept
                elif js == i:
                    c_val += h[j] * 1.0  # h[j] * (1-h[i]) = h[j] - h[j]*h[i], intercept part is h[j]
                else:
                    c_val += h[j] * (1.0 - h[js])
        intercepts[k] = c_val
    
    # Now find x in [0,1] that minimizes max_k (slopes[k]*x + intercepts[k]) * dx
    # Since dx > 0, minimize max_k (slopes[k]*x + intercepts[k])
    
    # Candidate points: 0, 1, and all crossing points
    candidates = [0.0, 1.0]
    for a in range(K):
        for b in range(a+1, K):
            if abs(slopes[a] - slopes[b]) > 1e-15:
                x_cross = (intercepts[b] - intercepts[a]) / (slopes[a] - slopes[b])
                if -1e-10 <= x_cross <= 1.0 + 1e-10:
                    candidates.append(np.clip(x_cross, 0.0, 1.0))
    
    best_x = 0.0
    best_val = np.inf
    for x in candidates:
        x = np.clip(x, 0.0, 1.0)
        vals = slopes * x + intercepts
        nv = vals.max()
        if nv < best_val:
            best_val = nv
            best_x = x
    
    return best_x
```

But this is O(K²) per coordinate = O(n²) per coordinate = O(n³) per sweep. For n=63: 63³ = 250K. That's very fast.

However, there's a subtlety: after changing h[i], the neighboring coordinates' optimal values change. So we need multiple sweeps. Also, coordinate descent on a non-separable objective might cycle or converge slowly.

But since the objective is the max of linear functions (in each coordinate), coordinate descent should converge. In fact, for this specific structure, it might converge quite quickly.

Let me also think about a "two-coordinate" optimization, where we optimize h[i] and h[j] jointly. The objective becomes the max of bilinear functions, which is not convex in the 2D space. So coordinate descent (one at a time) is safer.

Let me put together a more efficient solution that uses:
1. Coordinate descent (exact in each coordinate)
2. Smooth max gradient descent (for global direction)
3. Binary push (to explore structured solutions)

Let me write the final version:

Actually, I realize the coordinate descent approach with the inner loop over j for computing c_val is O(n) per (i, s) pair, making it O(n²) per coordinate and O(n³) per full sweep. For n=63, that's 63³ ≈ 250K per sweep, which is nothing. But the crossing point computation is O(K²) = O(125²) ≈ 15K per coordinate, making it O(n*K²) ≈ 1M per sweep. Still fine.

But wait, I can avoid the O(n) inner loop for computing c_val by using the relation:
c_val = c[k]_current - slope * h[i]

where c[k]_current is the current value of the k-th correlation (which I can precompute).

Let me precompute corr = np.correlate(h, 1-h, mode='full') once per sweep, and then for each (i, s):
intercept = corr[k] - slope * h[i]

This makes the coordinate computation O(K) instead of O(n*K), giving O(n*K) per sweep = O(n²) total. Much better.

Wait, but corr[k] changes as I update h[i]. So I need to recompute after each coordinate update. That brings it back to O(n) per coordinate (for the correlate call), O(n²) per sweep. Still very fast for n=63.

Let me write the final code now. I'll focus on:
1. Coordinate descent as the primary method (exact per-coordinate)
2. Smooth gradient descent for global moves
3. Binary push for structured exploration
4. Multi-restart for escaping local optima

Let me also handle the edge case where n is odd (like 63). In that case, n/2 = 31.5, so the sum constraint is sum(h) = 31.5. The solution can't be purely binary but can have one 0.5.

Actually wait, it can have any combination that sums to 31.5. Like 31 ones and one 0.5 and 31 zeros. Or 30.5 ones... no, that doesn't make sense. It could be 31 ones, 31 zeros, and one 0.5. Or 32 values of 0.5 and 31 values of 0 and 0. Hmm, many possibilities.

For the coordinate descent, the constraint is just sum(h) = n/2, which is handled by the projection.
