- Compute the value at h[i] = max(0, s-1) and h[i] = min(1, s)
- Also check the "breakpoints" where the max changes (but this is expensive)
- A simpler approach: just try h[i] = 0 and h[i] = 1 (and h[i] = s-0 and h[i] = s-1 for the other endpoint)

Actually, for the binary case, h[i] ∈ {0,1} and s ∈ {0, 1, 2}, so it's just the swap problem we already had.

For the continuous case, the coordinate descent approach is:
- Pick pair (i,j)
- Set h[i] + h[j] = s (current sum of these two)
- Find h[i] ∈ [max(0,s-1), min(1,s)] that minimizes max_k c[k]
- Update h[i] and h[j]

This is a 1D convex optimization (minimize a convex function over an interval), which can be done with ternary search or by finding the breakpoints.

For n=250, each evaluation of the objective takes O(n) time (compute all c[k] values). With ternary search (50 iterations), each pair update takes O(50n) = O(12500) operations. With n²/4 = 15625 pairs per sweep, that's ~195M operations per sweep. In numpy, this might be 10-20 seconds per sweep. Over 50 sweeps, that's 500-1000 seconds. Tight but feasible.

Actually, we don't need to try all pairs. We can use a greedy approach:
1. Find the current max (k*, c_max)
2. Find pairs (i,j) that would most reduce c[k*]
3. Update those pairs

This is much faster.

Let me think about this more carefully. The key insight is:

c[k*] = Σ_i h[i]*(1-h[i+k*])*dx

To reduce c[k*], we want to:
- Decrease h[i] where h[i+k*=0] (reduces the product)
- Increase h[i] where h[i-k*=1] (reduces the (1-h[i]) factor)

But we need to maintain sum(h) = n/2, so we increase some and decrease others.

This suggests a "flow" approach:
1. Identify "bad" positions: where h[i]=1 and h[i+k*]=0 (these contribute to c[k*])
2. Identify "good" positions: where h[i]=0 and h[i+k*]=1 (these would help if we set h[i]=1)
3. Move probability mass from bad to good positions

This is like a transportation problem!

def compute_c5(h, n):
    dx = 2.0 / n

def project_feasible(h, n):
    target = n / 2.0
    h = np.clip(h, 0.0, 1.0)
    for _ in range(100):
        diff = target - h.sum()
        if abs(diff) < 1e-12:
            break
        if diff > 0:
            room = 1.0 - h
            s = room.sum()
            if s < 1e-12:

            h = h + diff / s * room
        else:
            s = h.sum()
            if s < 1e-12:
                break
            h = h + diff / s * h
    return np.clip(h, 0.0, 1.0)

def smooth_max(c, alpha):
    m = c.max()
    sh = alpha * (c - m)
    sm = sh.max()
    return m + (sm + np.log(np.exp(sh - sm).sum())) / alpha

OK so the algorithm per swap attempt is:
1. Copy corr to new_corr: O(n)
2. Apply P_i: O(n) (two slice operations + one point)
3. Apply -P_j: O(n) (two slice operations + one point)
4. Compute max: O(n)

Total per attempt: O(n). For n=250, this is ~1000 numpy operations per attempt, which is very fast (~10μs).

The issue is: which (i,j) pair to try? If we try random pairs, we'll rarely find an improvement. We need a smarter strategy.

**Smart strategy**: 
1. Compute the current correlation and find the "hot" lags (where corr is near the max).
2. For each zero i, compute how much setting h[i]=1 would reduce the hot lags.
3. Pick the best i.
4. For the chosen i, find the best j (one position) to swap with.

Step 2: For zero i, the effect on corr is P_i (computed in O(n)). The new max would be:
max_k (corr[k] + P_i[k] - P_j[k]) for some j.

But we don't know j yet. A lower bound on the new max is:
max_k (corr[k] + P_i[k]) - max_k P_j[k] (loose bound)

Or we can just compute max(corr + P_i) as a proxy (ignoring the -P_j part). This underestimates the improvement from -P_j.

Alternatively, we can do:
1. For each zero i, compute R_i = corr + P_i: O(n) each, total O(n²)
2. Find i* = argmin max(R_i): O(n)
3. For i*, for each one j: compute max(R_i* - P_j): O(n) each, total O(n²)
4. Do the swap if it improves.

Total per improvement step: O(n²) ≈ 62K for n=250. In numpy, ~0.1ms per step.
With 100000 steps: ~10s. Very feasible!
