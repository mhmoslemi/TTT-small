**Goal** – Find 26 circles inside the unit square whose radii sum is as large as possible (≈ 2.637).  
The solution must respect the validator’s numerical tolerances and be produced by a self‑contained algorithm that does not rely on a global continuous optimizer like SLSQP.

The strategy below is *fully different* from the two previously proposed plans: it turns the geometric packing problem into a **Mixed‑Integer Linear Program (MILP)** on a discretised set of candidate centre locations, solves it with an off‑the‑shelf MILP solver (CBC via OR‑Tools), and finally refines the solution with a lightweight deterministic heuristic.  The MILP approach is a completely different formulation – it reduces the continuous position variables to a finite (but sufficiently dense) grid of possible centres and uses linear constraints to encode all feasibility conditions.

### 1.  Discretisation of the feasible region

1. **Grid size**  
   Choose a square lattice of side‑steps  
   \[
   \Delta = \frac{1}{k}
   \]
   with an integer `k` such that the resulting grid is fine enough to allow a packed configuration with a sum of radii close to the optimum but still small enough for the MILP to solve in time.  
   Empirically, `k = 20` (400 lattice points) works well:  
   * Each point `p = (i·Δ, j·Δ)`, 0 ≤ i,j < k.  
   * Max radius at a grid point is bounded by the distance to the nearest square side:  
     \[
     R_{\max}(p) = \min\{x,1-x,y,1-y\}.
     \]
2. **Candidate variables**  
   For every grid point `g` we introduce:  
   * a binary variable `b_g ∈ {0,1}` – 1 if a circle centre is chosen at `g`.  
   * a continuous variable `r_g ≥ 0` – radius of the circle if `b_g = 1`.  
   We add the linear coupling constraint  
   \[
   r_g \le b_g \cdot R_{\max}(g).
   \]
   This guarantees that when a location is unused, its radius is forced to zero.

--------------------------------------------------------------------
### 2.  MILP constraints

1. **Cardinality** – exactly 26 circles must be placed:
   \[
   \sum_g b_g = 26.
   \]
2. **Non‑overlap** – for every unordered pair of distinct grid points `g, h` that are *potentially colliding* we impose
   \[
   r_g + r_h \;\le\; \|g-h\| \;+\; M \bigl(2 - b_g - b_h\bigr).
   \]
   Here `M` is a large constant (e.g., `M = 2.0`) that deactivates the inequality unless both circles are selected (`b_g = b_h = 1`).  
   * **Reduction of pair constraints** – We pre‑filter pairs.  
     For `g, h` let  
     \[
     d_{\max}(g,h)= R_{\max}(g)+R_{\max}(h).
     \]
     If \(\|g-h\| \ge d_{\max}(g,h)\), then even with the largest permitted radii the circles cannot overlap, so the corresponding inequality is unnecessary.  
     This dramatically shrinks the number of pair constraints (from ~80k to a few thousand for `k=20`).
3. **Optional tightening** – For pairs whose distance is only slightly larger than `d_{\max}`, we can set a *smaller* big‑M:
   \[
   M_{gh} = \|g-h\| - d_{\max}(g,h) + \epsilon,
   \]
   where \(\epsilon = 10^{-6}\).  This gives tighter linear bounds and speeds up the solver.
4. **Linear objective** – maximise the total sum of radii:
   \[
   \max \; \sum_g r_g.
   \]
   The objective is linear and therefore compatible with the MILP framework.

### 3.  Solving the MILP

1. **Model construction** – Use the `ortools.linear_solver` interface (which bundles the CBC open‑source solver).  
   * Declare 400 binary variables `b_g` and 400 continuous variables `r_g`.  
   * Add all constraints described above.  
   * Set the objective to maximise \(\sum r_g\).
2. **Solver parameters** –  
   * `num_threads = 1` (the problem is small).  
   * `time_limit = 600` seconds (or less if the model is quick).  
   * `gap_tolerance = 1e-6` (forces high precision).  
3. **Retrieving a feasible solution** – CBC returns the best integer solution found within the time limit.  Even if the solver reports “infeasible” or “time limit reached”, the processor keeps the current best solution (`status = OPTIMAL` or `FEASIBLE`).  
4. **Post‑processing** – Extract `centers` and `radii` from the solution by selecting all grid points with `b_g = 1`.  Compute the numerical sum for reporting.

### 4.  Deterministic polish

The MILP solution is already a feasible packing that maximises the objective *over the discretised lattice*.  However, the discretisation may have constrained the circles to sub‑optimal positions.  To recover any additional slack we apply a tiny deterministic local improvement:

1. **Local radius + shift sweep** –  
   Similar to the “grow‑and‑shift” routine in the previous SA strategy, but now performed on the *actual continuous* circles obtained from the MILP.  
   * For each circle, repeatedly try to increase its radius by `δr = 1e‑4` while checking all feasibility conditions (boundary and pairwise overlaps) via squared distances.  
   * After all circles are grown as far as possible, perform a few passes of minor centre shifts (`±ε`, with `ε = 1e‑4`) that further reduce slack.

2. **Why this works**  
   The MILP already pushed every circle to its maximal radius *given its chosen grid point*.  A small shift can create new contact points with neighbours, thereby freeing up room for a neighbour to grow further.  The greedy sweep guarantees that any remaining slack is eliminated during the polish phase.

| Radius growth step `δr` | 1e‑4 | Tiny enough to avoid missed constraints yet fast enough for the polish phase. |
| Shift step `ε` | 1e‑4 | Allows sub‑pixel repositioning to exploit unused space. |
| Solver time limit | 600 s | Sufficient for CBC on a problem of ~480 variables and 3 k constraints. |
| Gap tolerance | 1e‑6 | Guarantees that the integer solution is essentially optimal for the discretised problem. |

### 6.  Expected performance and failure modes

| Potential failure | Symptom | Remedy |
|-------------------|---------|--------|
| MILP unsolvable (time limit) | Solver exhausts time without a feasible integer solution. | Reduce the grid density (`k = 15`) or tighten pair pruning aggressively; allow a lower `gap_tolerance`. |
| Solver returns sub‑optimal integer solution | Sum of radii far below target. | Increase solver `time_limit`; or run multiple solver restarts with different random seeds to explore the solution space. |
| Overlap after polish | Validator fails. | Tighten the feasibility check to use a stricter tolerance (`1e‑12`); re‑run the polish until no further improvements. |
| Radii drift out of bounds due to floating error | Radii slightly negative or centre outside the square. | Clamp radii to `[0, Rmax]` after each growth step; clip centres to the interior `[-r, 1-r]` box. |
| Excessive memory consumption | Too many pair constraints when `k` too large. | Apply more aggressive pair filtering (`dmax + ε`), or lower `k`. |
