**Objective** – Pack 26 circles inside the unit square so that the sum of their radii is as large as possible (target ≈ 2.637).  
The solution must satisfy the validator’s tolerance of 1 × 10⁻¹² on all positional and overlap checks.

The following plan is **completely different** from the earlier optimisation‑by‑gradient and simulated‑annealing approaches: we first *discretise* the possible circle centres to a fine lattice, formulate the geometry as a *Mixed‑Integer Linear Program* (MILP) that maximises the sum of radii, solve it with a standard MILP solver (CBC via OR‑Tools), and finally apply a lightweight deterministic polish to squeeze any remaining slack.  The MILP formulation turns all nonlinear feasibility conditions into linear inequalities, making the core optimisation a linear program over a small integer space.

--------------------------------------------------------------------
### 1.  Discretisation of the feasible region

1. **Grid generation**  
   Choose an integer `k` such that the square is subdivided into a `k × k` lattice of equally spaced points:  
   \[
   \Delta = \frac{1}{k},\qquad
   p_{ij} = (\,i\Delta,\; j\Delta\,),\; i,j = 0,\dotsc,k-1.
   \]  
   For the problem size, `k = 20` (400 lattice points) provides a fine enough resolution to allow a packing close to the optimum while keeping the MILP tractable.
2. **Maximum allowed radius per lattice point**  
   For each point `p = (x,y)` compute  
   \[
   R_{\max}(p) = \min\{\,x,\;1-x,\;y,\;1-y\,\}.
   \]  
   This is the largest radius a circle centred at `p` can have while staying inside the unit square.

--------------------------------------------------------------------
### 2.  Variables

For every lattice point `p` introduce two decision variables:

| Symbol | Type | Meaning |
|--------|------|---------|
| `b_p` | binary (`{0,1}`) | 1 iff a circle centre is placed at `p`; 0 otherwise. |
| `r_p` | continuous, `≥ 0` | Radius of the circle at `p` (zero if `b_p = 0`). |

To couple the two variables we add the linear constraint  
\[
r_p \;\le\; b_p \, R_{\max}(p).
\]  
Thus when a location is not used, its radius is forced to zero.

--------------------------------------------------------------------
### 3.  MILP constraints

1. **Cardinality** – exactly 26 circles must be selected:  
   \[
   \sum_{p} b_p = 26.
   \]

2. **Non‑overlap** – for every unordered pair of distinct grid points `p,q` that *may* collide we enforce
   \[
   r_p + r_q \;\le\; \|p-q\| \;+\; M_{pq}\, \bigl(2 - b_p - b_q\bigr).
   \]
   Here \(\|p-q\|\) is the Euclidean distance between the two lattice points, and \(M_{pq}\) is a large positive constant that effectively disables the inequality unless both circles are used.  
   **Pair filtering** reduces the number of such constraints dramatically:  
   * Compute \(d_{\max}(p,q) = R_{\max}(p)+R_{\max}(q)\).  
   * If \(\|p-q\| \ge d_{\max}(p,q)\) the circles would never overlap even with maximal radii; no constraint is needed.  
   * For pairs that *are* close we can tighten \(M_{pq}\) to  
     \[
     M_{pq} = \|p-q\| - d_{\max}(p,q) + \varepsilon,\quad \varepsilon = 10^{-6}.
     \]
     A tighter big‑M improves solver performance.

3. **Objective** – maximise the total radius sum:
   \[
   \max \;\sum_{p} r_p.
   \]

Every constraint is linear, so the entire problem is a standard MILP: integer variables for placement, continuous variables for radii, linear inequalities encoding geometry, and a linear objective.

--------------------------------------------------------------------
### 4.  Solving the MILP

Use the `ortools.linear_solver` interface (CBC solver).

* Create 400 binary variables (`b_p`) and 400 continuous variables (`r_p`).  
* Add all constraints generated in Section 3.  
* Set the objective to maximise `∑ r_p`.  
* Solver parameters:  
  * `num_threads = 1` (problem is tiny).  
  * `time_limit = 600` s (allow enough time for CBC to search).  
  * `gap_tolerance = 1e‑6` (forces near‑optimality).  
* Run the solver and capture its best integer solution (`status` may be `OPTIMAL` or `FEASIBLE`).  

After the solve, extract all lattice points `p` with `b_p = 1` and read their radii `r_p`.  These constitute the **coarse packing**.

--------------------------------------------------------------------
### 5.  Deterministic polishing

The MILP solution is already optimal for *the discretised* problem, but the lattice restriction may prevent slightly larger circles or better utilisation of the remaining space.  We therefore apply a small, deterministic refinement that treats the circles as truly continuous objects.

1. **Greedy radius grow** –  
   For each circle `i`:
   ```
   while True:
       r_try = r_i + δr
       if r_try violates boundary or overlap:
           break
       r_i = r_try
   ```
   Use a very small growth step `δr = 1e‑4`.  This loops until no further increase is possible with the current neighbour configuration.

2. **Minor centre shifts** –  
   Perform a handful (≈ 5) of passes.  In each pass:
   * Pick a random circle `i`.
   * Test small shifts in the 8 cardinal/diagonal directions by `ε = 1e‑4`.  
   * Accept a shift if all constraints remain satisfied.  
   This tiny repositioning can open a narrow gap that allows a neighbour to grow in the next radius‑grow pass.

3. **Repeat** the alternating grow‑and‑shift passes until a full sweep produces no improvement in any radius.

Because the polish uses only local feasibility checks (simple pairwise distance tests with a tolerance of 1e‑12), it is extremely fast compared to the global MILP solve.

--------------------------------------------------------------------
### 6.  Numerical safeguards & tolerances

* All coordinates and radii are stored as `float64`.  
* Feasibility tests use squared distances to avoid `sqrt` and compare against \((r_i+r_j)^2\).  
* A tolerance of `1e‑12` is added when checking overlaps, exactly matching the validator.  
* When increasing a radius or shifting a centre, values are clipped to keep the centre inside `[r, 1‑r]`.  
* The final solution is passed through the built‑in `validate_packing` function, which will raise an exception if any constraint is violated.
