Now, the coordinate descent step:
Given h and coordinate i, find δ ∈ [-h[i], 1-h[i]] that minimizes C₅(δ) = dx * max_k (c_k + δ*a_k).

Since this is the max of linear functions of δ, it's a convex piecewise-linear function. The minimum can be found by:
1. Ternary search (simple, works for any convex function)
2. Exact method: find the intersection points of the lines

Ternary search is simpler and sufficient. With ~50 iterations, we get high precision.

But actually, since it's piecewise linear, we can do better. The minimum of max_k (c_k + δ*a_k) over δ ∈ [δ_lo, δ_hi] occurs at:
- δ_lo or δ_hi (boundaries), or
- A point where two lines cross (a "kink")

The kink points are where c_k + δ*a_k = c_j + δ*a_j for some k, j, i.e., δ = (c_j - c_k)/(a_k - a_j).

There are O(n²) such points, but we can be smarter: sort the lines by slope (a_k), and the upper envelope can be found in O(n log n) time.

For n=400, even O(n²) = 160,000 is fast. But let's use a simpler approach:

Since the function is convex and piecewise linear, we can use a "bisection on the subgradient" approach:
- At δ, the subgradient is the set of a_k for k that achieve the max.
- If all a_k (for active k) > 0, move δ down.
- If all a_k (for active k) < 0, move δ up.
- If there exist active k with a_k > 0 and active j with a_j < 0, we're at (or very near) the minimum.

This is like a subgradient method but it converges in one step for piecewise linear functions (if we can find the exact crossing).

Actually, the simplest correct approach for piecewise linear convex minimization:
1. Evaluate f(δ_lo) and f(δ_hi)
2. Find the δ where the "slope" changes sign. The slope at δ (from the right) is max_{k: c_k+δ*a_k = f(δ)} a_k.

Or even simpler: just do a fine grid search combined with binary search.

For n=400, the evaluation of f(δ) = max_k (c_k + δ*a_k) takes O(n) time. A ternary search with 60 iterations takes O(n * 60) = 24,000 operations. For 400 coordinates, that's 9.6M per pass. At ~10^9 ops/s, that's ~0.01s per pass. We can do hundreds of passes.

But wait, there's a catch: after we update h[i], all the c_k values change (since c_k depends on all h[n]). So we need to recompute c_k for each coordinate update. That's O(n) per update (computing the correlation), so O(n²) per pass total.

Actually, we can be smarter: if we only change h[i] by δ, we can update c_k incrementally:
c_k(new) = c_k(old) + δ * a_k (where a_k is computed from the OLD h)

So we don't need to recompute the full correlation! We just add δ * a_k to each c_k.

This makes each coordinate update O(n) time (compute a, find optimal δ, update c). Total per pass: O(n²). For n=400, that's 160,000 operations per pass. Extremely fast.

    offset = n - 1
    dx = 2.0 / n
    target = n / 2.0
    h = h.copy()
    c = c.copy()  # current correlation values
    
    for pass_num in range(n_passes):
        improved = False
        for i in range(n):
            # Compute a_k for this coordinate
            a = np.zeros(2*n - 1)
            
            # First term
            k1_start = max(i - (n-1), -(n-1))
            k1_end = min(i, n-1)
            if k1_start <= k1_end:

Wait, I have a bug. The ternary search bounds are [-h[i], 1-h[i]], and any δ in this range gives h[i]+δ ∈ [0,1]. So after the ternary search, δ_opt is guaranteed to be in [0,1] for h[i]+δ_opt. No clipping needed.

But there's another issue: after updating c and h[i], the next coordinate's `a` vector should be computed from the UPDATED h. Since I'm computing `a` inside the loop (after the previous update), this should be fine.

However, there's a subtle issue with the incremental update of c. When I update h[i] by δ, the new correlation is c_new = c_old + δ * a. But this is only correct if a was computed from the old h. Since I compute a from the current h (which includes all previous updates in this pass), and then update h[i] and c, the next coordinate will see the updated c. This is correct for Gauss-Seidel style coordinate descent.

Let me also think about the order of coordinates. Random order might help avoid cycling.

Let me also add: after the coordinate descent, do a SLSQP refinement to handle the non-smoothness at the "kinks" of the max function.

Now, one concern: the ternary search assumes the function is unimodal, which is true for convex functions. But the function max_k (c_k + δ*a_k) is convex (max of linear functions), so ternary search is valid.

However, there's a numerical issue: if multiple k's achieve the max simultaneously, the function is non-differentiable at that point, but it's still convex, so ternary search works.

Let me also think about whether we can speed this up. The bottleneck is the `np.max(c + δ * a)` computation inside the ternary search. This is O(n) per evaluation, and we do ~50 evaluations per coordinate, for n coordinates total. So O(n² * 50) = O(8M) per pass for n=400. That's fine.

Actually, I realize I can do even better. Since f(δ) = max_k (c_k + δ*a_k) is the maximum of lines, I can find its minimum more efficiently:

The minimum of max_k (c_k + δ*a_k) over δ ∈ [lo, hi] can be found by:
1. Sort the lines by slope a_k
2. The upper envelope changes at intersection points
3. The minimum of the upper envelope is at a specific intersection point

But this is O(n log n) per coordinate, vs O(n * 50) for ternary search. For n=400, both are fine. Let me just use ternary search for simplicity.

Actually, there's an even simpler exact method for 1D piecewise linear convex minimization:
- The minimum is at the "median" slope in some sense. Specifically, the subgradient at δ is the convex hull of {a_k : c_k + δ*a_k = f(δ)}. The minimum is where 0 is in the subgradient, i.e., min_{active} a_k ≤ 0 ≤ max_{active} a_k.

Algorithm:
1. Start with δ = some initial value (e.g., midpoint of [lo, hi])
2. Find the active set: S = {k : c_k + δ*a_k = f(δ)} (within tolerance)
3. If max_{k∈S} a_k < 0: the function is decreasing, move δ up
4. If min_{k∈S} a_k > 0: the function is increasing, move δ down
5. Otherwise: we're at the minimum

But finding the exact active set and the crossing point requires more work. Let me just stick with ternary search.

Let me now think about the overall algorithm:

```
1. h = initial_h_values, project to feasible
2. c = compute_corr(h)
3. Run coordinate descent (many passes)
4. Run SLSQP with log-sum-exp smoothing
5. Repeat 3-4 a few times
6. Return best
```

def compute_corr(h):
    return np.correlate(h, 1.0 - h, mode='full')

def compute_c5(h):
    n = len(h)
    dx = 2.0 / n
    return float(np.max(compute_corr(h))) * dx

def project_feasible(h, target_sum):
    h = np.clip(h.astype(float), 0.0, 1.0)
    for _ in range(300):
        diff = target_sum - np.sum(h)
        if abs(diff) < 1e-15:
            break
        if diff > 0:
            mask = h < 1.0
        else:
            mask = h > 0.0
        cnt = int(mask.sum())
        if cnt == 0:
            break
        h = h.copy()
        h[mask] += diff / cnt
        h = np.clip(h, 0.0, 1.0)
    return h

def _compute_a(h, i, n, offset):
    a = np.zeros(2 * n - 1)
    k1_start = max(i - (n - 1), -(n - 1))
    k1_end = min(i, n - 1)
    if k1_start <= k1_end:

        a[ks + offset] += 1.0 - h[i - ks]

    if k2_start <= k2_end:
        ks = np.arange(k2_start, k2_end + 1)
        a[ks + offset] -= h[i + ks]
    return a
